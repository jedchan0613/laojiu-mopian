# 手机端档案快捷维护功能方案

编写日期：2026-10-17  
适用项目：老旧默片  
文档状态：待评审方案，尚未实施  
本次交付：本文档及开发日志；不代表功能开发、线上部署或真实档案发布授权。

## 一、方案结论

优先完善现有网页版档案工作台，让管理员用安卓手机浏览器完成日常维护。沿用现有管理入口、档案数据和发布流程，通过手机布局和操作流程的改进实现快捷维护。

首期重点是：**快速找到一件档案，修改文字或图片，明确知道是否已经保存，再按原有规则决定是否发布。**

独立安卓 App 暂不开发。网页版可以复用现有服务，也减少安装包、应用更新和系统适配的维护工作。浏览器书签可作为快捷入口；独立安装体验、离线编辑和桌面图标应用另行评估。

本文中的“作品”统一对应项目现有的“档案／藏品”，不另建一套作品数据。

### 实施前需要核对的实际问题

1. 本机和服务器上的代码版本、档案数据及图片副本可能不同；手机线上维护以服务器私有数据为准，本地预览以本机数据为准，二者不会因本方案自动同步。
2. 开发前确认工作副本完整、状态稳定，尤其是 `site/package.json`、正式字典和构建脚本；不自行还原或删除用户文件。检查期间的临时文件状态变化另记开发日志，不据此判断线上是否故障。
3. 当前隐私页代码包含“按既有设置默认选中”的确认方式。本方案建议手机发布流程改为逐项主动确认，这是需要评审的行为变化，不能写成已经实现。
4. 目前没有完成用户实际安卓手机上的登录、输入法、相册选择、上传和发布全流程测试。

## 三、使用对象、目标和范围

### 3.1 使用对象

使用者为现有获准管理员。网站普通注册用户继续使用已有投稿流程，普通账号不因本功能获得修改正式档案、查看内部资料或发布的权限。

### 3.2 优先解决的场景

| 场景           | 手机上的期望操作                             |
| ------------ | ------------------------------------ |
| 发现题名或简介有错    | 搜索档案 → 快捷编辑 → 保存草稿                   |
| 补充年代、标签或图片说明 | 打开档案 → 修改常用字段 → 保存草稿                 |
| 调整展示图片       | 查看图片 → 设为首图／前后移动／替换 → 保存草稿           |
| 开始整理一件新藏品    | 填入藏日期、类型、题名 → 建立草稿 → 后续继续补全          |
| 临时有空继续整理     | 打开草稿列表 → 看到上次保存时间和待补项 → 继续编辑         |
| 修改完成准备公开     | 查看变更 → 补齐必填项 → 人工隐私确认 → 检查并发布 → 查看结果 |

### 3.3 首期包含

- 手机档案列表、搜索、常用筛选、速览和草稿入口。
- 常用字段快捷编辑，以及现有完整编辑能力的手机适配。
- 已筛选发布副本的选择、查看、排序、说明、替换和移除。
- 手动与自动草稿保存、明确的保存状态、登录和网络异常处理。
- 多设备版本冲突保护、重复提交防护和操作结果核对。
- 单件发布前检查、变更对照、完整人工隐私确认和结果反馈。

### 3.4 首期不包含

- 独立安卓安装包、应用商店发布、离线档案库或后台持续上传。
- 批量自动发布、多个档案同时编辑、批量套用公开状态。
- 拍摄原始扫描件后直接入站、手机扫描、自动裁切、图片修复或自动脱敏。
- AI 识字、人脸识别、身份推断或自动补写档案内容。
- 新数据库、新云服务、新 Node.js 包，或另建后台／CMS。
- 投稿审核、账号管理和联系收件箱的全面手机重做；保留现有入口即可。
- 主库管理、本地与服务器的自动双向同步、历史数据批量整理。

## 四、手机页面和导航设计

### 4.1 总体结构

沿用 `/admin/`，根据屏幕宽度使用手机布局，不另建 `/m-admin/` 或另一套业务页面。电脑端保留现有工作台结构；手机布局以约 760px 为设计起点，实施时结合现有 900px、680px 规则统一检查，避免新旧样式相互覆盖。

手机通过现有 HTTPS 线上管理入口访问。本机 `127.0.0.1:4173/admin/` 只能由运行服务的电脑访问，手机即使连接相同 Wi-Fi 也不能直接使用。不得为真机测试把监听改为 `0.0.0.0` 或开放管理端口；前三阶段先做本机浏览器模拟，真机验证安排在用户授权的第四阶段。

手机主导航只保留三个常用入口：

| 入口 | 内容                               |
| -- | -------------------------------- |
| 档案 | 默认列表、搜索、筛选、新建档案                  |
| 草稿 | 已保存且尚未发布的草稿、上次保存时间、待补项           |
| 更多 | 维护概览、历史与回收、投稿审核、账号与申请、联系收件箱等已有入口 |

编辑页使用专门的底部保存栏，替换列表页导航的位置，避免两组固定栏叠在一起。

### 4.2 档案列表

手机打开后默认显示列表，不自动选中并打开第一件档案。首屏包含页面标题、搜索框、“筛选”和“新建档案”，其下直接显示档案。

每行显示：缩略图、题名、显示年代、类型、状态；永久编号放在次要位置但必须能完整查看。已有草稿的档案显示“有未发布修改”，将公开版本与编辑状态区分开。

常用筛选为类型、年代、状态；更多筛选放入可关闭的面板。支持“年代未知”，沿用现有筛选定义，不在本次重分类历史档案。筛选、分页和排序仍使用原有规则；已有分页继续使用，首期不改成无限滚动。

从编辑或速览返回后，恢复原搜索条件、页码和滚动位置。搜索词可能包含人物信息，不放入第三方分析、公开日志或可分享链接；页面内存足以保存本次列表状态。

### 4.3 档案速览

速览显示图片、题名、编号、年代、公开状态、草稿状态与待补项，提供三个明确入口：

- **快捷编辑**：修改常用内容。
- **完整编辑**：访问全部现有字段和管理分区。
- **查看公开页**：仅已有公开页面时显示，明确当前查看的是公开版本。

有草稿时，速览必须注明“正在查看草稿”，避免把尚未发布的内容当作访客已经看到的内容。已撤销记录继续只读，按原流程恢复为草稿后才能编辑。

### 4.4 编辑页示意

```text
返回    编辑档案                    更多
题名／永久编号
已有未发布修改 · 已保存 14:32

常用信息    图片    完整资料    发布检查

题名
[输入框]
显示年代
[输入框]
公开简介
[多行输入框]
标签
[已选标签与添加入口]

底部：有未保存修改      [保存草稿] [下一步]
```

示意中的四个入口是手机呈现方式，内部继续映射原有编辑分区。“发布检查”依次提供预览、变更对照、待补项和隐私检查，不删除现有分区能力。

## 五、快捷编辑和新建档案

### 5.1 常用信息

快捷编辑默认显示题名、显示年代、公开简介和标签；图片说明在图片区维护。确有需要的其他现有字段，可在用户试用后调整位置，不先扩充字段数量。

- 年代无法判断时，可明确选择“年代未知”；不猜测年份。
- 标签内部继续保存为数组，不用分号字符串替代。
- 编号只读；更改年代或属性不改变永久编号。
- “收藏品编码”由正式规则计算，不增加手工编码入口。
- 类型专属字段仍按现有 schema 显示，中文标签来自正式代码字典。
- 快捷页只隐藏不常用字段的显示，不清空、裁掉或重置这些字段。

保存必须以完整加载的当前记录为基础，仅修改明确变更的字段；不能把快捷页当作全新空记录提交。未展示的 `core`、`metadata`、`public_view` 内容和图片说明应完整保留。

### 5.2 完整资料

“完整资料”包含原有基本管理字段、对应类型的对象专属信息和公开文字等。参与收藏品编码的专属必填字段集中前置；其他字段按原有分组折叠。

发布必填项缺失时可以继续保存合法草稿，但发布检查必须准确列出缺失项。点击缺失项，应展开其分组、滚到字段并显示中文原因，不只在顶部显示一段错误。

代码规则以 `docs/reference/archive-metadata-standard-v1.xlsx` 及项目正式字典为准。本方案不新增代码、维度或“手机专用”档案属性。

### 5.3 新建档案

新建先收集当前保存草稿所需的三个条件：

1. 入藏日期：解释为接收／获得日期，不能与拍摄、书写或发行年代混淆。可以提供“使用今天”按钮，但不能悄悄以今天代替未知的实际日期。
2. 藏品分类及必要的正式精确类型：沿用现有分类到类型的对应关系。
3. 题名：允许用户输入暂定题名，不由程序编造。

填写后点击“建立草稿”，由服务器统一分配永久编号。显示年代、其余必填项和图片可随后补全；不足以发布时明确显示待补项。

不满足草稿最低条件时，提示“尚未建立草稿，还缺……”，不能显示“已保存”。首次保存失败或响应丢失后，先查询本次操作结果，不立即重新分配编号。

## 六、图片维护

### 6.1 选择与接收

提供“选择发布副本”，调用手机系统的相册／文件选择界面。首期不增加“拍摄后直接发布”。选择前说明这里只接收已筛选、压缩并完成必要脱敏的发布副本。

保持当前 JPEG、PNG、WebP 范围，单张上限 30 MB、线上每次保存新增图片合计约 60 MB。超限时列明具体文件并提示先保存一批；不静默丢图、不自动转格式、不扩大限额。HEIC、TIFF、RAW 等给出中文原因和外部制作发布副本的提示。

浏览器的文件类型过滤只是选择提示，不能替代服务端检查；继续执行真实文件类型、内容校验及已有安全检查。参见 [MDN：文件选择的 accept 属性](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/accept)。

文件名、体积或格式正常不能证明不存在敏感内容。用户还须检查图像内容及附带的定位等私密信息；无法确认时暂停接收，先在项目之外准备合适的发布副本。不承诺自动发现所有隐私问题。

### 6.2 图片卡片

每张图片显示缩略图、顺序、首图标记、说明和保存状态，并提供：

- 点按放大，保留清晰的关闭、上一张、下一张按钮。
- “前移”“后移”“设为首图”，不用长按拖动作为唯一排序方式。
- 修改说明、替换发布副本、从草稿移除。

“设为首图”通过现有图片顺序实现，不另存一套封面字段。调整顺序时，图片说明必须跟随对应图片移动；边界按钮停用并说明原因。

### 6.3 上传、失败和取消

沿用逐张二进制上传，手机默认同时上传一张，降低内存和网络压力。显示真实可知的“第 2／5 张”“已接收”“草稿写入中”，没有字节级依据时不显示虚假的百分比或剩余秒数。

区分三个状态：

| 状态      | 含义                      |
| ------- | ----------------------- |
| 已选择，未保存 | 文件仍只在当前页面，本次修改尚未完成服务器保存 |
| 已暂存     | 服务器已接收文件，但尚未确认写入档案草稿    |
| 已保存到草稿  | 草稿及图片引用均由服务器确认，重新打开后应可见 |

某张失败时保留页面内容和每张处理结果。有效的已暂存令牌可继续使用，只重试失败或令牌已失效的图片；这需要补全令牌状态核对，不能把当前实现描述为已经支持断点续传。服务器重启或令牌过期时，明确提示重新上传。

取消操作沿用现有安全取消流程，确认结果后再解除忙碌状态。未写完的临时文件与已保存草稿分开处理；不删除已保存图片。

### 6.4 移除与替换

移除、替换先成为草稿修改，公开版本继续显示原图。正式发布和构建成功后，旧发布副本才进入现有回收区；不提供永久删除按钮。恢复图片或历史仍然只生成草稿。

图片接收继续走现有私密暂存和待入站通道。本地对应 `public-assets/inbox/`；线上对应已配置的私有 inbox。不能为了手机方便直接上传至 `site/public/` 或其他公开目录。

## 七、保存可靠性和中断处理

### 7.1 保存状态

页面持续显示状态，不能只用转瞬消失的提示：

| 状态   | 用户看到的文字示例        | 允许的下一步            |
| ---- | ---------------- | ----------------- |
| 尚未保存 | 有尚未保存的修改         | 手动保存或继续编辑         |
| 保存中  | 正在保存草稿…          | 文字可继续编辑，提交类操作避免重入 |
| 保存成功 | 已保存到线上草稿 · 14:32 | 返回列表或继续编辑         |
| 保存失败 | 尚未保存：网络连接中断      | 保留页面，核对后重试        |
| 登录失效 | 需要重新登录，当前修改尚未保存  | 发起登录，返回原页核对       |
| 版本冲突 | 此档案已在其他页面更新      | 查看差异，不能直接覆盖       |
| 结果未知 | 请求已发出，正在核对是否保存成功 | 查询结果后再决定重试        |

本地模式显示“本机草稿”，线上模式显示“线上草稿”。“已保存”仅指服务器已确认的对应版本，不代表公开网站已更新。

### 7.2 自动保存

建议调整现有约 30 秒的自动保存方式：没有待传的新图片时，停止输入约 5 秒触发一次保存；连续编辑时约每 30 秒尝试保存一次完整、合法快照。中文输入法还在组词时不打断输入。

存在尚未提交的新增／替换文件时，暂停自动保存，提示“有图片待上传，请保存草稿”。用户点击后统一上传和保存，避免在移动网络下意外开始大批传输，也避免只保存一半图文状态。此项属于对现有自动保存行为的调整。

自动保存正常时不弹遮挡全屏的忙碌层；失败时显示持续状态及重试入口。草稿最低条件不全、登录失效、已有提交操作、确认对话框打开时不启动自动保存，也不反复请求。

每次保存固定一个内容快照和编辑序号。保存期间若用户继续输入，旧响应只能确认旧快照，不能覆盖新输入或将新修改标成“全部已保存”；后续再保存最新内容。

### 7.3 返回、切后台和断网

- 页面内返回、切换档案或离开编辑时，有未保存修改则提供“保存并返回”“继续编辑”“放弃本次未保存修改”。保存成功后才返回；放弃不删除此前已保存草稿。
- 浏览器返回键纳入同样处理。保留 `beforeunload` 作为补充，但不能把它当成手机防丢失的唯一措施。
- 切到后台时，可在条件允许时尽力保存轻量草稿；不在后台启动图片上传或发布，不宣称必然保存成功。
- 回到前台先核对登录、操作结果和服务器版本，再继续保存，不能无条件上传旧页面内容。
- 断网时保留当前页面内容并清楚提示。网络恢复是重新核对的信号，不能仅凭浏览器“在线”状态宣称保存成功。

手机切换应用可触发页面可见性变化，可用于上述处理；这一事件不等于后台网络请求一定完成。参见 [MDN：visibilitychange 事件](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)。

首期不把档案正文、图片或身份凭证持久写入 `localStorage`、IndexedDB 或离线缓存。因此，浏览器被系统强制关闭、页面刷新或手机重启后，**最后一次服务器确认保存之后的内容仍可能丢失**。产品说明和验收须明确这一边界，不承诺完全离线防丢。

### 7.4 登录过期

保留 Cloudflare Access 和服务端二次身份核验。服务端按现有规则验证每个受保护请求；不把管理员密钥或 Access 凭证交给页面另行保存。Cloudflare Access 的授权依赖受保护域名的授权 Cookie，参见 [Cloudflare：授权 Cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/)。

识别可判断的 401／403、登录重定向和非 JSON 登录页面；无法区分跨域登录拦截与网络失败时，显示“需要检查登录或网络”，不假定某一种原因。

由用户点击“重新登录”，优先在同一浏览器另开登录页，保留原编辑页面。返回后重新核对权限、服务器版本和未完成操作；不自动重发发布请求。若原页面已被系统回收，只能恢复服务器上已确认保存的草稿。

## 八、多设备冲突和重复操作保护

这部分是手机与电脑交替维护的必要条件，必须同时覆盖电脑端的相关写入，不能只在手机界面弹提示。

### 8.1 防止旧内容覆盖

1. 读取档案时，服务器返回一个不可自行修改含义的版本标记，覆盖对应正式记录、草稿及图片引用等影响编辑的状态。
2. 保存、发布、撤销、恢复等写入携带读取时的版本标记；在同一受控写入范围内重新读取并比较，匹配后才写入。
3. 不匹配时返回明确冲突，保留手机当前输入，提供服务器最新内容与本次修改的对照。
4. 首期不自动合并、不提供强制覆盖。用户核对后基于最新记录重新应用需要保留的修改。

版本标记和操作状态属于私有维护信息，不进入档案正式 `core`、`metadata`、`public_view` 或公开构建。保存、发布、撤销与恢复要共用写入协调；仅增加比较而不约束读写时序，不能通过验收。

### 8.2 防止重复提交

复用并补充现有操作编号机制，为保存、发布建立可查询的结果。操作编号表示“这一次提交”，同一操作重试应返回原结果；同一编号与不同内容组合必须拒绝。

- 新建草稿：同一次保存重试返回同一个永久编号，不能创建第二件。
- 发布：重复点击、网络超时或返回前台不能触发第二次构建。
- 已完成操作：显示原结果；处理中：显示进行中；无法确认：先核对，不盲目重放。
- “取消请求已发出”与“服务器确认取消完成”分开显示，不能把本机中断连接当成服务器回滚成功。

若现有内存记录不足以覆盖响应丢失或服务重启，增加小型私有文件记录，使用 Node 内置文件能力，不引入数据库或新依赖。记录只保存必要的操作编号、目标编号、请求摘要、状态、结果和时间，不保存正文、图片内容、敏感号码或登录凭证。

文件记录放在已受控的管理私有数据目录，不写入仓库或公开目录；重启后无法证明已完成的操作标为“待核对”。清理策略只处理这一新增技术记录，不连带清理档案、草稿、图片或历史。具体目录权限和容量策略在实现阶段明确。

## 九、发布检查和隐私保护

### 9.1 发布流程

```text
保存草稿
  → 查看本次修改及待补项
  → 查看手机发布前预览
  → 逐项人工隐私确认
  → 明确点击“检查并发布”
  → 服务端校验、正式构建及既有部署切换
  → 显示结果，打开公开页复核
```

只有进入发布检查的最后确认步骤，才显示最终发布按钮；常用编辑页的主要按钮始终为“保存草稿”。保存和发布使用明确不同的文案。

修改已发布档案时，显示“原公开内容 → 本次修改”的逐项对照。手机上采用纵向内容块，避免需要横向拖动的宽表格。未修改项目不重复列出，但完整记录仍保留。

### 9.2 必须保留的门禁

- 按 `archive-data/metadata-template.json` 和正式 Excel 规范检查字段。
- 核对永久编号、目录、图片路径、图片存在性、代码有效性及类型与 schema 的对应关系。
- `LET`、`RPR`、`OTH` 沿用通用元数据；其他类型使用现有对应 schema，不平铺所有类型维度。
- 证件及旧卡片公开字段继续遵守遮盖规则，不因手机输入方便增加完整敏感字段。
- 新草稿和修改稿保持隔离，`Y`／`R` 不默认公开；仅人工明确批准且检查通过，才允许形成正式发布状态。
- 正式发布必须在完整 `site/` 中执行现有 `npm run build`；失败时按已有机制恢复，不能把“草稿保存成功”当成“发布成功”。
- 线上更新继续使用既有安全发布流程；管理页面、草稿、历史、回收区、操作记录不得进入 `site/dist/`。

### 9.3 人工确认的建议变化

建议 13 项检查默认未确认，显示已完成数量；每项可点开说明，但不能隐藏检查内容。提交前必须由用户主动确认，不能用“快捷发布”代替。

这与当前代码中的默认选中方式不同，应作为本方案评审中的明确行为变化。实现时统一电脑与手机的确认规则，避免两端标准不同；本次编写方案不改动既有设置。

确认须绑定本次具体的图文版本。确认后再修改文字、类型或图片，必须使对应确认失效；服务端也要核对最终发布版本，不能只依赖页面上的勾选结果。

涉及敏感项目、可识别真实人物或不确定风险时，按照 `docs/privacy-checklist.md` 和 `docs/intake-sop.md` 暂停，交由用户判断。程序不主动寻找身份，也不凭年代久远就自动批准。

2026-10-12 特别授权只适用于授权所指的 LJM-20261011 批次已入站档案。不能把编号日期相同、以旧档案为模板新建或手机新上传解释为自动获得授权；每次实际依据该授权的操作仍须写入开发日志。

### 9.4 发布结果与中断

显示真实阶段：“检查中”“构建中”“切换中”“已完成／未完成”。短期先保留已有同步发布机制，通过受保护的操作结果查询改善恢复，不另建后台任务服务。

切后台、掉线或超时后显示“发布结果待核对”，通过操作编号核对服务器最终状态；不得直接提示成功、失败或再次发布。只有服务端确认构建和必要切换完成，才显示“已发布”。

取消和失败沿用原有恢复机制。撤销、历史恢复和回收区保留现有独立入口，不加入默认快捷操作栏，也不增加永久删除能力。

- 已知字段的小修改，从编辑到保存不需要切换多个分区。

- 自动保存成功时不抢输入焦点；任何时候都能看出是否还有未保存修改。
- 每条失败说明给出一个能执行的下一步；不预先承诺固定上传速度或发布耗时。

## 十四、上线、回退和评审重点

### 14.1 上线与回退

沿用现有管理服务和部署流程，不新增服务器端口或放开本地监听。部署前确认代码版本、私有目录权限，以及原有草稿、历史、待入站区和回收区的保留情况。

如果版本核对成为新的写入要求，新版前后端须配套发布；旧页面收到明确刷新提示，不能因为没有版本参数就继续无保护写入。新操作记录不混入正式档案，旧程序回退时也不能顺带删除。

遇到保存异常、冲突判断错误或图片引用异常，停止本次维护，保留现场并使用既有回退方式处理。回退代码不等于回退用户数据，不自动覆盖回退前后产生的新草稿；涉及数据恢复时先核对具体对象和影响。

上线后的试用顺序：只读查找 → 编辑批准样例并保存 → 重开核对 → 人工检查并发布批准样例 → 核对公开页与历史。未得到具体授权，不对真实档案执行发布、撤销或不可逆清理。

### 14.2 方案评审时需明确的选择

以下已有推荐方案，供评审时确认；本次不要求立即操作：

| 事项 | 推荐选择 | 原因 |
| --- | --- | --- |
| 产品形式 | 优先手机网页版 | 复用现有入口与档案管理能力 |
| 首期默认动作 | 保存草稿 | 日常修改更快，公开仍需明确决定 |
| 自动保存 | 文字等轻量修改加快保存；新增／替换文件手动提交 | 减少中断损失和意外流量 |
| 隐私确认 | 改为逐项主动确认，并与本次版本绑定 | 防止旧勾选沿用到已改变的图文；此项与既有默认选中设置不同 |
| 离线能力 | 首期不做持久离线保存 | 避免在手机新增一份敏感档案副本及复杂同步机制 |
| 第一轮试用设备 | 用户实际安卓手机和常用浏览器 | 用真实输入、选图和前后台行为验收 |
