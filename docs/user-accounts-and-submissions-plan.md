# 老旧默片：注册用户与自主投稿初版方案、开发执行提示词

方案日期：2026-09-26。

当前状态：仅完成方案，尚未执行开发、安装依赖、创建数据库或部署。用户已选定“邮箱验证码，注册登录合一”。本文其余数值为初版建议值，不代表已经实施。

## 一、初版产品方案

### 1. 产品定位

让普通访客方便地保存喜欢的档案、提交自己的资料，并持续查看处理进度。公开浏览无需注册；用户提交的资料先进入私密审核区，经过站主审核、整理和明确批准后，才进入公开网站。

网站继续承担“公开展示发布副本”的职责，不成为用户的高清档案主库或原始资料备份盘。

### 2. 已有基础与实施边界

项目已有 Astro 公开网站、免注册投稿、私密收件、凭回执查询、投稿审核、转为档案草稿、正式发布检查、联系与撤下入口、点赞和本机浏览足迹。注册模块应扩展这些能力，不重复建设投稿系统。

现状依据：`docs/submission-guide.md`、`docs/privacy-checklist.md`、`docs/intake-sop.md`、`docs/online-admin-deployment-guide.md`、`site/src/layouts/BaseLayout.astro`、`local-admin/submissions.mjs`。

项目文档同时存在“本地管理限制”和已记录的线上管理部署说明。文件记录不等于本轮获得部署授权，实施时必须先核实真实环境和有效授权；不得自行把本地管理入口暴露到公网。本轮方案也不解除 AGENTS.md 对数据库、新依赖、服务和 API 的限制。

### 3. 用户看得到的功能

| 模块 | 初版包含 | 界面处理 |
| --- | --- | --- |
| 注册与登录 | 邮箱验证码、首次开通、保持登录、退出 | 一个“登录 / 注册”入口 |
| 我的投稿 | 新建、保存草稿、提交、查看进度、补充材料、撤回、申请修改或撤下 | 登录后默认页面，主按钮为“上传档案” |
| 我的收藏 | 收藏与取消收藏、跨设备查看 | 简单图片列表，不设文件夹 |
| 账户设置 | 昵称、邮箱管理、退出全部设备、重要通知偏好 | 一页完成，不收集多余资料 |
| 处理提醒 | 待补充、处理结果、已公开、撤下结果 | 放在对应投稿中，并显示待处理数量 |
| 帮助与权益 | 上传说明、授权、隐私说明、联系、数据导出与注销申请 | 就近提示，低频入口放页脚或设置 |

用户中心只设“我的投稿、我的收藏、账户设置”三个主要入口。帮助不再单独做大型栏目，通知不再单独建设消息中心。

### 4. 完整使用路径

访客浏览公开档案 → 登录或开通账户 → 上传发布副本并填写简短说明 → 保存草稿或提交审核 → 查看进度、按需补充 → 站主审核整理 → 正式发布成功 → 用户看到公开链接。

关键区别：上传成功只代表资料已收到；审核通过只代表进入整理；只有正式发布成功，才显示“已公开”。

### 5. 初版暂不包含

不做评论、私信、关注、粉丝、积分、等级、徽章、付费会员、支付、电商、公开个人主页、自定义头像上传、共同编辑、批量导入、AI 识别、自动身份推断、自动公开、原始高清文件托管、视频音频及 PDF 上传。

继续保留原有点赞逻辑，收藏与点赞各有用途，不在本阶段改造点赞计数。浏览足迹继续只留在当前浏览器，不自动同步到账号。

### 6. 设计方向

沿用网站现有暖纸底、深墨色、中文衬线标题、少量朱红和档案展签风格。表单和操作文字使用现有清晰的无衬线字体。账户页面保持留白和图片感，不使用密集统计卡、排行榜、复杂侧边栏或大型管理面板。

桌面用户中心采用简短横向导航；手机采用紧凑分段导航和单列内容。投稿卡片显示封面、题名、状态、最近更新时间以及当前最需要完成的一项操作。

默认文案：“把一段记忆，交给时间保存。”“资料收到后会先由站主核对，未经确认不会公开。”正式实施时结合现有文案语气调整，不承诺审核时限或永久保存。

### 7. 建议技术方向

保留 Astro 公开页面，复用现有 Node.js 投稿接收和审核流程；增加独立隔离的账户能力。若核实仍为单服务器、小规模部署，优先评估 SQLite 保存账号、会话、收藏与投稿归属关系，图片仍保存在私密文件目录，正式档案仍以现有规范为准。SQLite 官方将多数中低流量网站列为适用场景，但多实例与高并发写入需要另行评估。[SQLite 官方适用场景](https://www.sqlite.org/whentouse.html)

这只是待确认的技术建议。账户持久保存、邮件发送和私密备份会增加维护工作；邮件服务与存储可能产生持续费用。第一阶段应提供具体选型、维护责任、费用口径和退出迁移办法，获得授权后再引入。不能为了维持“零依赖”而自行拼装不可靠的身份认证。

## 二、可直接交给 Codex 的完整执行提示词

从下文“任务开始”到“任务结束”可整体复制使用，也可以直接让我按照本文件执行指定阶段。本文提供完整初版范围，但每轮只执行一个明确阶段；没有指定阶段时，从阶段一开始。

---

**任务开始**

请为“老旧默片”实施一个简洁、有设计感、适合初创网站的注册用户与自主投稿模块。注册登录采用我已选定的邮箱验证码方式。请按以下要求工作，不自行扩展产品范围。

### A. 开始前与工作方式

1. 先阅读项目根目录及相关子目录的 AGENTS.md，以及投稿、隐私、入站、数据规范、管理部署和开发日志。先确认现有功能、实际运行环境与当前改动，保护用户已经完成的工作。
2. 所有说明优先用简单中文。较大修改前说明准备修改什么、影响什么；每阶段完成后自行检查并更新 `docs/development-log.md`。
3. 本任务是完整初版任务书，不是自动执行所有阶段的授权。只完成本轮明确指定的阶段；未指定时只执行阶段一。不要提前执行下一阶段、提交、推送或部署。
4. 阶段一需要把新依赖、数据库、邮件服务、必要在线接口的用途、维护成本、费用与风险整理成可审阅清单。只有取得对应授权后才能实施，不能自行修改 AGENTS.md 来解除限制。
5. 不改动项目之外的档案主库，不复制原始扫描件、TIFF、RAW 等主档。真实档案与真实用户资料不得作为测试数据。
6. 复用现有 Astro 页面、投稿接收、审核、联系和发布机制，不另建 CMS，不把整个网站重写成大型应用，不添加未经要求的框架或服务。

### B. 角色与权限

只需要三种角色：访客、普通注册用户、站主管理员。

- 访客可以继续浏览、搜索和查看公开档案，使用既有联系、纠错及免注册投稿入口。
- 注册用户可以管理自己的账户、收藏和投稿，包括私密图片；不得读取其他用户的资料。
- 管理员可以审核投稿、处理账户限制和权益申请，并按现有流程发布。普通账号与管理员身份验证必须分开，普通账号不能通过修改请求参数取得管理权限。
- 所有数据和文件权限由服务器逐项检查。隐藏按钮、不展示链接、难以猜测的编号都不能替代权限验证。
- 暂停账号后立即停止新的登录、上传和编辑；保留可用的申诉、导出及注销联系途径，不连带永久删除其资料。

### C. 页面与导航

优先沿用既有路由和布局，以下是建议分工，不要求机械照搬地址：

- `/login/`：注册登录合一。
- `/me/submissions/`：我的投稿，登录后的默认入口。
- `/contribute/`：复用现有投稿页，登录后提供账户投稿能力，未登录时保留原有免注册投稿。
- `/me/submissions/<投稿编号>/`：查看详情、处理记录、补充或修改。
- `/me/favorites/`：我的收藏。
- `/me/settings/`：账户、安全、通知与权益入口。
- 协议和隐私说明使用稳定、可访问的页面；复用现有帮助、联系和撤下说明。

主导航只增加登录入口；登录后显示“我的”。用户中心保持三个主要栏目，不另外增加数据看板、消息中心或社交主页。登录成功返回原先操作的位置，只允许站内安全跳转。

用户中心的通用页面框架可以作为静态页面输出，但不得含任何真实用户资料。实际私密内容必须登录后读取；账户页面不进入站点地图，私密接口和图片禁止公共缓存。禁止搜索收录不能替代身份验证。

### D. 邮箱验证码注册与登录

1. 输入邮箱、获取验证码、完成验证。首次验证成功后进行简短开通确认：阅读并主动同意服务与隐私说明，可填写昵称，也可采用不含邮箱信息的默认昵称。已注册用户直接登录。
2. 不要求手机号、真实姓名、性别、生日、住址、身份证、头像或密码。邮箱始终私密，不能从邮箱自动推导公开昵称。
3. 首次开通记录协议版本和同意时间；发布授权在每件投稿中另行确认，不能用注册协议替代。
4. 验证码初始建议为 6 位、10 分钟有效、一次使用；重发间隔 60 秒，每个验证码最多尝试 5 次。重发后旧验证码失效，重发不能清空累计滥用限制。
5. 按邮箱、来源地址和全站邮件额度共同限流，记录最少必要信息。错误、过期、频繁发送、服务不可用应给出清楚提示；验证前不透露邮箱是否已注册。验证码不能出现在日志、网址或公开响应里。
6. 验证码绑定邮箱、验证目的和本次验证事务；保存不可直接还原的校验值，校验成功、尝试计数与使用作废须防止并发重复使用。采用成熟认证组件及安全随机数，不设计自己的加密算法。
7. 建议登录状态闲置 7 天、最长 30 天到期，以服务器为准；退出当前设备、退出全部设备必须真正撤销登录凭证。换邮箱、注销、导出等敏感操作需近期重新验证。
8. 换邮箱必须验证原邮箱和新邮箱，提示冲突、通知原邮箱并撤销旧会话；收不到原邮箱验证码时进入人工恢复流程，不凭昵称、公开资料或提交过的照片自动找回。
9. 邮件未配置时明确说明登录服务不可用；测试验证码只能在隔离测试环境使用，生产环境必须拒绝启用测试绕过方式。

邮箱验证、验证码有效期和账号变更的安全实现参考官方安全建议；本产品把邮箱验证码限定为普通用户登录，管理端继续使用既有更严格的身份验证。[OWASP 邮箱验证建议](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html)

### E. 上传与填写：三个简单步骤

**第一步：选择资料。**

- 继续接受 JPG、PNG、WebP，1—8 张，每张不超过 5 MB，单件合计不超过 20 MB；拒绝 TIFF、RAW、SVG、PDF、压缩包、动画和多页图片。
- 显示缩略图、顺序、封面、移除按钮和清楚的上传状态；手机上可以用上下移动按钮调整顺序，不强迫拖拽。
- 选择图片先做本地预览。用户点击“保存草稿”或“提交审核”后才上传，并在页面说明这点；不要用户刚选文件就悄悄上传。
- 超限明确指出哪张图片及原因，重复图片提示确认。成功上传的部分可保留到草稿，失败图片单独重试；不需要大文件分片和复杂断点续传。
- 首次上传强调只提交筛选、压缩和必要脱敏后的副本，网站不负责保存原始档案。

**第二步：填写说明。**

| 字段 | 初版要求 |
| --- | --- |
| 题名 | 必填，建议不超过 60 字 |
| 藏品分类 | 必选，显示已有分类的中文名称 |
| 资料介绍 | 必填，建议不超过 2000 字 |
| 大致年代 | 可选，不知道可选“年代未知” |
| 大致地点 | 可选，提示不要填精确私人住址 |
| 来源与展示授权依据 | 必填，使用简短说明或现有选项，未知可如实说明并交人工核实 |
| 可识别真实人物情况 | 必选“有 / 无 / 不确定”；选择“有”或“不确定”时交人工判断 |
| 单张图片说明 | 可选，便于说明正面、背面或细节 |
| 公开署名 | 默认匿名，可主动填写本件投稿的署名 |

昵称、登录邮箱、投稿署名相互独立。更改昵称不能自动改写已发布署名；联系方式不进入公开字段。每件投稿只代表一件对象，可包含其多张图片，不把数件不相干藏品混为一件。

不要要求普通用户填写永久编号、21 维元数据、内部编码、研究状态或管理字段。投稿人提供自然语言，站主整理为正式档案规范；这不代表降低正式发布的必填要求。

**第三步：预览并确认。**

- 分别展示拟公开的图片、题名、说明与署名，以及仅站主可见的来源说明。
- 保留“保存草稿”和“提交审核”两个清楚的操作。
- 用少量、具体、未预勾选的确认项说明发布副本、授权范围和已知隐私风险；不能把用户勾选声明当成人工隐私检查通过。
- 沿用现有非独家、限本站整理及展示的授权边界，压缩、裁切、必要遮盖须说明；不自动扩展为出售、转授权或其他商业使用。
- 提交成功后显示独立投稿编号、当前状态和返回“我的投稿”的入口，不承诺固定审核天数。

### F. 保存、状态与后续修改

初版提供明确的“保存草稿”按钮和保存时间。保存成功的内容支持跨设备继续；未保存的表单与图片不写入浏览器长期存储，离开页面前提醒。后台保存失败不得显示已保存。

| 用户看到的状态 | 含义与允许操作 |
| --- | --- |
| 草稿 | 仅本人和获授权的管理员可见，可编辑、保存、提交、移入回收区 |
| 待审核 | 已收到，查看回执与提交版本，可撤回后修改 |
| 待补充 | 显示站主说明，补充资料后重新提交 |
| 整理中 | 初审通过，正在补齐正式档案，尚未公开；可提交补充说明或停止处理申请 |
| 已公开 | 只有发布成功后显示，提供公开链接，可申请修改或撤下 |
| 暂不采用 | 显示简短理由；允许补充的情况可修改后再次提交 |
| 已撤回／已停止处理 | 保留处理记录，不再进入发布；确需重投时重新提交并重新审核 |

“修改审核中”“撤下处理中”等用本件投稿的附加提示表达，不必增加多个复杂列表栏目。已撤下内容提供处理结果，不继续展示失效的公开缩略图。

内部继续保留现有审核状态含义。例如“初审通过”映射为用户看到的“整理中”，不能改名后误认为已经发布。公开状态应根据关联档案真实发布结果取得，不手工维持另一套相互矛盾的状态。

提交后保留只读版本，审核必须针对确定的内容版本；补充、换图和修改产生新版本，旧的审核批准不能直接套用。并发编辑发生冲突时提示刷新，不覆盖较新内容。重复点击、网络超时重试不得生成重复投稿。

撤回与审核、转入和发布操作必须互斥或重新校验；已收到的停止处理申请阻止后续发布。已经转成档案草稿的投稿沿用现有停止处理机制，不简单退回为可自由编辑的投稿。

已公开档案的修改申请生成新草稿，经重新审核和构建后替换；未通过前保留当前公开版本。涉及隐私的撤下申请优先处理，并阻止再次发布；不要把“已收到申请”显示成“已经撤下”。完成撤下要检查详情、图片、缩略图、搜索数据、站点地图及相关缓存，保留私密历史，不修改主档。

删除草稿或移除已保存图片，先说明具体对象与影响，再进入私密回收流程。不得永久删除已保存档案图片；正式发布副本的替换回收、历史恢复继续遵循现有规则，恢复只生成草稿。

### G. 收藏、提醒与账户权益

**收藏：**在公开档案详情增加收藏或取消收藏；未登录时引导登录并返回原档案，必要时提示继续刚才的操作。收藏默认私密，以永久档案编号关联，重复点击不会产生重复记录。已撤下档案显示“暂不可查看”，不保留其敏感缓存图片。初版不做收藏夹、公开收藏榜或批量整理。

**提醒：**待补充、暂不采用、已公开、修改或撤下结果都写入投稿详情，并在“我的投稿”显示需要处理的数量。重要进度邮件由用户选择，默认不勾选；登录验证码和账户安全通知单独处理。邮件不附私密图片、完整投稿内容或联系方式，提醒用户登录查看。发送失败可以重试但不回退审核结果、不重复执行发布。暂不做短信、微信推送和营销邮件。

**账户设置：**提供昵称、已验证邮箱、更换邮箱、退出全部设备、通知偏好、申请导出、申请注销；默认头像用现有图形或文字，不开放图片上传。

**导出：**初版可人工处理，需验证本人并提供私密下载方式，仅含其账户信息、收藏和提交的发布副本，不包含管理员内部备注、其他用户资料或档案主库内容。不把“收到申请”说成“导出完成”。

**注销：**再次验证后，明确展示账户、私密投稿、公开署名、已公开内容与备份的处理方式；收到申请后撤销会话、停止新投稿，并提供回执。初版由站主按既定流程完成并反馈，处理中与已完成要区分。注销不自动等于删除所有已公开档案，也不能静默保留实名署名或把个人数据无限期留在回收区。

上线前必须形成可执行的保留、匿名化、删除及备份到期处理规则，写清负责人与处理时限。遵守项目关于已保存图片不可随意永久删除的要求；确需不可逆清理时先说明对象、原因、范围和影响，取得相应授权。撤下、删除和注销三个申请不能混为一谈。

### H. 站主需要的最小管理功能

在现有受保护的审核入口增加必要信息，不新建一套大型后台：

- 识别账号投稿与免注册投稿，查看投稿人账号状态和对应投稿。
- 查看图片、来源说明、授权记录、提交版本；按现有审核规则处理。
- 给投稿人发送可见的处理说明，内部备注仍只给管理员看。
- 完成待补充、初审通过、暂不采用、停止处理和发布结果衔接。
- 处理账号暂停与恢复、邮箱恢复核实、数据导出、注销、修改及撤下申请；重要操作记录时间、操作者、原因与结果。
- 查看私密收件容量、邮件发送失败、待处理申请等必要运行信息，不做复杂数据分析系统。

普通用户与管理员的接口、凭证和权限边界必须分开。公众投稿接收进程不能读写档案主库、管理历史或正式发布目录。

### I. 数据结构与正式入站

1. 账号、登录会话、收藏、投稿归属、用户申请属于私密业务数据，不混入公开档案的 `core`、`metadata` 或 `public_view`。明确每类数据的唯一真实来源，避免两份审核状态或联系方式互相覆盖。
2. 账号内部编号、`TG-` 投稿编号、正式 `LJM-YYYYMMDD-TYP-NNN` 档案编号彼此独立。投稿不立即获得正式档案编号，不因账号注销或资料分类改变而重编永久编号。
3. 网络上传时间不能直接当作永久编号里的接收或获得日期。阶段一先明确数字供稿的接收口径；不把收到照片副本误写成站主获得实物。公开来源说明只写已核实的事实。
4. 所有未审核文件进入独立私密收件区，不能存入 `site/public/`、`site/dist/`、`public-assets/` 或能被静态服务访问的目录。私密图片只能由本人或获授权管理员读取。
5. 人工筛选、脱敏并通过隐私检查的发布副本，才允许进入 `public-assets/inbox/`，再复用现有转草稿及发布流程。不得把公网直传目标设为 inbox，更不能直接写入网站素材目录。
6. 正式档案仍使用 `core` 通用字段与 `metadata` 专属 schema；字段、代码、必填维度以 Excel 规范为准。多值使用数组，未知采用已定义的未知代码或规范允许的原始文字，不补造代码。
7. 自动生成 `collection_code`，分类属性变化只重算该编码，不修改永久 `item_id`。初审通过不得直接把隐私状态设成 G 或发布状态设成 U3。
8. 正式发布仍需完整字段、对象类型与 schema、有效代码、图片路径、逐项隐私检查及站主明确批准。只有达到 `privacy_level = G`、`record_status = ACT` 并满足现有规则后，才能进入正式发布。
9. 每次正式发布在 `site/` 执行完整 `npm run build`，保留现有历史备份与发布回退机制；构建或公开版本切换失败，当前公开版本保持可用，投稿状态不得显示“已公开”。
10. 存在完整身份或金融号码、电话、精确私人地址、清晰签名、医疗信息、未成年人、可识别真实人物或不确定风险时，停止自动转入和发布，交站主人工判断。不得主动识别人脸、猜测身份或进行联网寻人。

### J. 老投稿与现有功能兼容

- 继续保留免注册投稿及已有“投稿编号＋查询密钥”查询、停止处理能力；本阶段不强迫老用户注册。
- 已登录用户新投稿直接关联本人账号，不再要求重复填写私密联系方式。
- 如提供“关联以前的投稿”，必须同时验证已登录账号及原投稿编号、密钥，并让用户明确确认。仅凭相同邮箱、昵称、公开信息或上传图片相似，不能自动认领。
- 一个投稿只能归属一个账号，已认领冲突交人工核实；丢失原密钥不能凭猜测找回。关联操作保留审计记录。
- 初版关联成功后保留原回执能力，并提示用户继续妥善保管原密钥。邮箱或昵称修改不得改变归属。
- 不破坏现有联系、纠错、搜索、筛选、点赞、浏览足迹、管理历史与回收机制。

### K. 安全、容量与运行要求

**登录与权限：**使用 HTTPS；登录凭证放在带 `HttpOnly`、`Secure` 和合适 `SameSite` 设置的 Cookie 中，服务端可撤销，不写入浏览器长期存储。防止跨站伪造请求、会话固定和不安全跳转；私密响应禁止共享缓存，用户退出后清理页面内的私密资料。相关实现参考 [OWASP 会话管理建议](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

**文件接收：**服务端验证真实文件类型、实际解码、大小、总量、图片像素和处理耗时；不能仅相信后缀及浏览器声明。沿用最长边不超过 2400 像素的 JPEG 发布候选副本与 4000 万像素输入上限，去除 EXIF/GPS 等内嵌信息，随机生成存储文件名，禁止路径穿越、可执行文件和脚本内容。图片重编码不等于遮盖画面文字或消除人物隐私，仍需人工检查。参考 [OWASP 文件上传建议](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)。

**容量：**在现有频率、并发和全站容量保护上，增加账号级配额。建议初始上限为每天提交 10 件、同时保存 20 件未提交草稿，账号未公开资料占用不超过 200 MB；具体值在阶段一结合真实服务器容量确定。存储统计包括草稿、投稿、历史版本和回收数据的实际占用，不能反复删除重传来绕过容量控制。对用户只显示剩余额度和超限原因，不增加复杂空间管理界面。

**可靠性：**文本安全转义、服务器校验、请求大小限制、上传与认证限流必须有效；纯文本即可，不引入富文本编辑器。写入采用可恢复方式，账号关联与文件保存遇到失败不能遗留可被他人读取的数据。私密记录、密钥、邮件内容不得进 Git、构建产物、公开日志和统计服务。

**运营：**制定数据库与私密文件一致备份、恢复演练、容量预警、邮件失败重试和依赖更新的简短操作说明。备份仍为私密资料。提供关闭新注册或暂停新上传的应急开关，但不影响公开浏览，也不能把服务故障显示为提交成功。不擅自把来稿上传给第三方图片审核或 AI 服务。

### L. 视觉与交互验收

- 复用现有暖纸底、深墨色、少量朱红、衬线标题、无衬线操作文字和字体资源；不新增 UI 组件库或字体服务来实现简单页面。
- 每个页面有清楚标题、简短说明和一个主要操作；低频内容折叠，表单错误定位到对应字段。
- 投稿卡片保持图片与展签感，状态用文字加样式表达，不能只靠颜色；缺少图片时使用中性的占位样式。
- 表单有真实标签、键盘焦点、可读错误提示和足够点击面积。验证码支持粘贴，不用难操作的拆分输入格。
- 覆盖加载、空列表、无结果、保存成功、上传部分失败、发送失败、验证码过期、登录过期、配额不足、权限不足和服务维护等状态。
- 桌面 1440px、手机 390px、窄屏 320px 均无横向溢出，手机输入和软键盘不遮住必要操作。弱网时不丢失已成功保存的数据，不假装剩余未上传内容已保存。
- 公开首页与档案页不为账户模块加载大体积无关脚本，保持当前图片、搜索和字体性能。

### M. 分阶段执行与交付

**阶段一：可审阅的原型与技术定案。**

先完成现状核对、复用清单、缺口与规则冲突说明，再制作隔离的本地假数据界面原型，涵盖登录、三个用户栏目、上传流程和主要异常状态。原型只能放在明确的私有预览位置，不能进入公开构建；不得假装提供真实身份验证或接收真实来稿。尽量用现有工具，不安装新依赖。

同时提交具体的认证组件、私密存储、数据库、邮件发送、部署隔离、数据流向、备份、保留与注销处理方案；列明新增项、维护成本、费用、需要用户配置的内容、授权变更和验收办法。完成可审阅结果后再提出确实必要的确认，已有授权不要重复询问。本阶段不创建数据库、不配置真实邮件服务、不执行线上变更。

**阶段二：账户、收藏与基础权益。**

在已批准选型及必要例外范围内，实现注册登录、权限隔离、账户设置、收藏、退出和安全措施，并打通人工导出及注销申请。使用隔离测试账号，完成身份验证与跨用户访问检查。不得自动进入上传开发或公开上线。

**阶段三：账户投稿与审核衔接。**

实现草稿、上传、版本、进度、补充、旧投稿关联、通知和最小管理扩展；打通原有私密收件、inbox、档案草稿、审核和发布流程。用虚构资料演练成功、失败与恢复全过程。

**阶段四：上线前验收与有限开放。**

执行完整回归、正式构建、备份恢复演练，准备可核对的部署与回退清单，确认协议、邮件可达性、容量限制、隐私隔离和应急关闭能力。只有取得对应线上操作授权后才部署和开放；先限制新注册或投稿规模，验证实际运行后再扩大。没有授权时交付已检查的部署材料并停止。

每阶段交付：完成内容、可查看成果、检查结果、已知限制、下一阶段所需条件，以及更新后的中文开发日志。不要为了填满报告而重复执行无关测试。

### N. 必须通过的最终验收

1. 新用户开通、老用户登录、验证码过期与重试、换邮箱、退出全部设备和受限账号均符合约定。
2. 用户 A 无法通过修改编号、文件地址、请求参数或缓存读取和修改用户 B 的投稿、图片、收藏及权益申请；普通账号不能调用管理员接口。
3. 上传格式、真实内容、大小、像素、文件数量、恶意文件名、请求频率及容量限制均由服务端生效。
4. 保存草稿后可恢复；断网、重试、重复点击、多个窗口编辑不会静默丢失内容、重复投稿或覆盖已审核版本。
5. 用虚构资料完成“投稿→待补充→重提→初审→转草稿→人工发布检查→成功公开”，每一阶段的公开状态真实准确。
6. 构建失败、发布切换失败、发布过程中申请停止处理、已公开内容申请修改或撤下均有正确结果；审核通过的旧版本不能替换成未经审查的新图片。
7. 私密数据和未审核素材未进入 `site/dist/`、公开静态目录、站点地图、公共缓存、分享图片或可公开读取的历史版本。
8. 原免注册投稿与回执继续可用，旧投稿关联不发生越权；联系、纠错、搜索、筛选、点赞、本机足迹和管理流程没有回归。
9. 邮件失败不丢投稿、不重复发布；配额满或服务未配置时明确提示，不出现虚假成功。
10. 注销、导出、公开署名处理与私人资料保留规则能够实际执行，收到申请和处理完成区分清楚。
11. 桌面及手机浏览器关键流程、键盘操作、所有必需状态和实际新文案字体覆盖检查通过。
12. 现有相关测试与 `site/` 中完整 `npm run build` 通过；保留可恢复备份、检查发布产物并报告真实结果，不能用“页面能打开”代替验收。
