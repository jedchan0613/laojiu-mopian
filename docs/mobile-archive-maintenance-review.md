## 一、评估结论

方案可行，应在现有网页版档案工作台上继续完善。电脑和手机共用 `/admin/`、同一套档案结构、草稿与发布流程；根据屏幕大小调整页面。继续使用现有 HTML、CSS、JavaScript 和 Node 内置能力，预计无需新增框架、Node 包、数据库或云服务。

已有的搜索、筛选、速览、草稿中心、图片说明与排序、正式构建、历史和回收能力可以复用。新增工作的重点是手机操作路径、保存期间继续输入、网络或登录中断后的核对，以及多设备同时维护时的保护。工作量不能按“只改手机样式”估算。

建议将原方案四阶段调整为**五个执行阶段**：将原第二阶段拆成“服务端写入保护”和“手机保存与上传”，其余方向保留。本轮只完成评估；附件中的功能建议与操作步骤不视为用户已经批准开发、部署或发布。

## 三、实施前必须明确的修正

### 1. 先约束写入，再开放真实手机维护

静态检查发现：发布读取草稿后，另一页面仍可保存同件新草稿；发布结束按路径清除草稿，可能清掉后来保存的修改。这是潜在竞态，未以真实档案复现，也无证据认定已有数据丢失。

应将同件档案的保存、发布、撤销、恢复放入共同的写入协调，并在实际写入前重新比较版本。编号分配仍须防止两次新建占用同号；多个档案的发布还涉及共同的网站数据和构建，不能只加单件检查。发布后的清理只能处理本次已确认版本。

现有批量发布、投稿转草稿、相册操作和外语发布也要检查接入边界。这不意味着重做这些功能，而是防止旧入口绕过新保护或与全站构建相互干扰。`local-admin/batch-intake.mjs` 等现有调用工具须适配新写入协议；命令行数据重建及自动部署另列运维互斥核对，不扩大为新的手机功能。

### 2. 操作编号不能简单沿用为单一去重键

当前前端同一个操作编号贯穿逐张上传、保存和发布。若直接规定“同编号、不同内容一律拒绝”，会把正常的下一步骤也拦住。实现时需明确整次操作与每个子请求的编号关系，并绑定目标与请求摘要。

新增私有操作记录仅保存必要的编号、目标、摘要、状态、结果和时间，不保存档案正文、图片或凭证。目录、权限、容量和清理范围在第二阶段明确，并排除代码仓库和公开产物。重启后无法证明完成的操作进入“待核对”，不能自动重新建档或重新发布。

当前取消接口发出中止信号后即可返回，没有等待保存／恢复结束。“请求取消”不能显示成“已经取消并恢复”；写入完成但响应中断时，仍须核对服务器终态，不以手机断开连接判断草稿是否存在。

### 3. 隔离环境要覆盖所有数据和构建路径

前四阶段使用完整的隔离工作副本和虚构、无隐私的测试资料。必须逐项隔离正式JSON、草稿、inbox、上传暂存、历史、回收区、译文、账号／投稿等私有目录，以及网站生成数据、图片、构建输出与公开版本目录；只换一个草稿目录不够。

环境核对清单是第一阶段开始工作的前置条件。不得以真实维护目录作测试夹具，不自动同步本机与服务器。只监听 `127.0.0.1`，不为手机测试开放局域网端口。

### 4. 保留现有业务，明确三项行为变化

- 原方案的手机四个编辑入口须完整映射现有分区，保留外语内容及相册等能力；首期不额外重做这些页面。
- 快捷编辑以完整记录为基础修改选中字段；永久编号、其他专属字段、公开投影、图片说明及未展示属性不能丢失。
- 建议采用文字轻量自动保存、图片手动提交；具体5秒／30秒时机需以中文输入和异常测试核验。
- 建议把13项改为主动确认，确认绑定具体图文版本，内容改变后重新确认；不沿用旧页面勾选。
- 建议新建时明确实际入藏日期，今天通过明确选择使用，不能替代未知日期。

上述均为本次评估建议，本轮未改变既有行为。既有特殊授权只针对其明确批准的旧档案，不按编号日期自动扩展给新图、新件或新模板。

## 四、建议的五个执行阶段

每次只执行用户明确指定的一阶段。阶段通过后更新开发日志，提交该阶段结果并停止；未通过时先在当前阶段修复。

| 阶段 | 主要工作 | 完成条件与停止点 |
| --- | --- | --- |
| 一：手机界面与操作路径 | 先核对并建立隔离环境；完善档案／草稿／更多导航、默认列表、快捷字段、完整资料入口、图片卡片和窄屏检查页；保留相册与外语入口 | 提供可操作本地样例及桌面回归记录；320—430px、768px和桌面无整页横向溢出；此时只用于界面验收，停止交用户看效果 |
| 二：服务端写入保护 | 共同写入协调、版本比较、新建编号保护、可查询的操作结果与重复提交防护；接入保存、发布、撤销、恢复等现有写入入口；定义私有操作文件和旧页面兼容处理 | 隔离测试证明旧版本不能覆盖新版本，发布不会清掉新草稿，同次重试不重复建档或构建；缺版本的旧客户端明确要求刷新；停止交付安全验收记录 |
| 三：手机保存、中断与图片恢复 | 保存快照及持续状态；文字自动保存与中文输入；未保存离开处理；登录／断网／前后台核对；图片逐张状态、令牌查询、失败重试及取消 | 隔离演练中旧响应不覆盖新输入；待传图不自动上传；暂存与已保存明确区分；超时先查结果；原草稿及图片保持可恢复；停止交付编辑流程验收 |
| 四：发布流程与上线前验收 | 手机纵向变更对照、待补项定位、图文版本绑定的人工确认、发布结果核对；构建失败、历史和回收保护；检查桌面、相册和六语言兼容 | 仅用隔离的非敏感样例完成发布／失败／恢复演练；在完整隔离副本的 `site/` 执行现有 `npm run build` 并通过公开隔离检查；形成使用说明、部署与回退清单；安卓真机项仍标待验 |
| 五：单独授权上线与安卓真机试用 | 按明确授权部署到既有受保护入口；先只读，再保存批准样例，最后仅对明确批准的样例检查并发布；核对线上结果与回退方式 | 记录实际安卓系统、浏览器、网络和日期；完成登录、输入法、选图、软键盘、切后台、冲突与发布结果复核；完成后停止 |

原方案四阶段与本建议对应：原阶段一＝新阶段一；原阶段二＝新阶段二＋三；原阶段三＝新阶段四；原阶段四＝新阶段五。

## 五、各阶段的检查重点

- **第一阶段**：对应原A02、A03的界面部分、A07的图片操作、A17的窄屏模拟及A18电脑回归；不能据此宣称保存可靠性通过。
- **第二阶段**：重点A04、A11、A12及A16的共同写入保护；增加“发布期间另存新稿”“旧入口／脚本未带版本”“同操作分步请求”场景。
- **第三阶段**：重点A03、A05—A10；用可控制的延迟、错误和中断演练，检查未显示字段保留、输入焦点及图片说明跟随。
- **第四阶段**：重点A01、A13—A16、A18；服务端必须实际阻止缺项、无效代码、未确认／旧版本发布，不能只隐藏按钮。
- **第五阶段**：在实际安卓手机复验相关A01—A18，尤其登录、相册选择、中文输入、软键盘、锁屏与切后台；不能用电脑缩窄窗口代替真机结论。

保存、并发和重试使用实际行为测试；不为每条样式写重复实现的测试。可复用现有 `local-admin/tests/album-relation-tools.test.mjs` 的隔离目录和真实HTTP测试方式。现有发布器的部分Linux切换测试在Windows跳过，第四阶段不能将跳过项计为通过，须在第五阶段授权后的Linux环境补验。

第四阶段正式构建必须通过所有既有公开检查，产物不包含管理页面、草稿、操作记录或私密数据。发布功能及共享服务改动完成时也应执行该阶段适用的既有测试和正式构建检查，不能将已发现的失败留到上线前处理。

## 六、使用边界与上线条件

“已保存草稿”和“已公开发布”始终分开。本机显示本机草稿，线上显示线上草稿。手机网页不持久保存档案正文、图片或凭证；浏览器被强制关闭后，最后一次服务器确认之后的输入仍可能丢失。

文件选择的格式提示不能代替服务端内容检查；切后台事件也不保证网络请求完成。方案对此保持谨慎是合理的，已核对 [MDN文件选择说明](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/accept) 和 [MDN页面可见性事件说明](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilitychange_event)。既有登录保护继续使用受保护域名的授权机制，参见 [Cloudflare授权Cookie说明](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/)。这些资料支持设计约束，不代表本项目已通过安卓兼容测试。

前三项建议行为、私有操作目录和接口细节应在对应阶段说明清楚后实施。预计不需新增依赖；若出现新依赖、服务器配置或资料迁移需求，按项目规则单独说明，不混入手机样式修改。

第五阶段开始前须重新核对服务器代码、数据路径、保留目录、部署状态及磁盘空间，不能沿用旧文档中的版本号和件数。本机 `127.0.0.1:4173/admin/` 不能直接由手机访问；真机使用既有HTTPS管理入口。上线涉及推送、应用部署、服务重启或配置改变时，在具体动作明确后取得单独线上授权。

评估当时未修改程序、档案、图片、草稿、隐私确认或服务器设置，没有执行构建、真实入站、发布、撤销、恢复或数据清理。当时建议从“一：手机界面与操作路径”开始；后续执行状态以本文顶部及阶段验收记录为准。
