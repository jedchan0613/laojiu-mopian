# 注册用户与自主投稿：阶段三实施方案（账户投稿与审核衔接）

方案日期：2026-09-27。
对应总方案：`docs/user-accounts-and-submissions-plan.md`（2026-09-26）阶段三。
前置交付：阶段一（原型与技术定案）、阶段二（账户、收藏与基础权益，已完成）。
本文件是阶段三的实施设计说明。

---

## 一、目标范围

方案 M 阶段三原文：

> **账户投稿与审核衔接。** 实现草稿、上传、版本、进度、补充、旧投稿关联、通知和最小管理扩展；打通原有私密收件、inbox、档案草稿、审核和发布流程。用虚构资料演练成功、失败与恢复全过程。

拆解为 9 个功能点：

1. **草稿**：保存、跨设备继续、未提交草稿与已提交投稿分开；离开页面前提醒。
2. **上传**：本地预览后才上传；1—8 张、每张 ≤ 5 MB、合计 ≤ 20 MB；部分失败可单独重试。
3. **版本**：提交后保留只读版本；补充、换图、修改产生新版本；旧的审核批准不能套用到新版本。
4. **进度**：用户可见状态由内部状态映射得出；"已公开"以公开档案真实发布结果为准。
5. **补充**：待补充状态下补充资料或说明后重新提交。
6. **旧投稿关联**：必须同时验证已登录账号 + 原投稿编号 + 原查询密钥，并明确确认。
7. **通知**：重要进度邮件由用户主动开启，默认关闭；邮件不附私密图片、完整投稿内容或联系方式。
8. **最小管理扩展**：审核入口识别账号投稿、显示投稿人账号状态、发送可见处理说明。
9. **打通既有流程**：账户投稿沿用私密收件区 → 人工隐私检查 → 转档案草稿 → 正式发布检查 → 发布的既有链路。

**明确不做**（属阶段四）：线上部署、服务器数据目录、Caddy 路由、发布切换演练。也**不做**评论、私信、公开个人主页、批量导入、AI 识别。

## 二、状态模型（用户可见状态如何得到）

| 用户看到 | 判定条件 | 允许操作 |
| --- | --- | --- |
| 草稿 | `status = draft` | 编辑、保存、提交审核、移入回收区 |
| 待审核 | `status = pending` | 查看提交版本、撤回后修改 |
| 待补充 | `status = needs_info` | 查看站主说明、补充后重新提交 |
| 整理中 | `status = approved` 且未公开 | 提交补充说明、申请停止处理 |
| 已公开 | 关联档案编号出现在**公开档案数据**中 | 申请修改、申请撤下 |
| 暂不采用 | `status = declined` | 查看理由；允许时修改后重新提交 |
| 已撤回 / 已停止处理 | `status = withdrawn` | 保留处理记录，不再进入发布 |

附加提示（不新增栏目）：`withdrawal_requested` → "撤下处理中"；`change_request` 未完成 → "修改审核中"。

关键约定：

- "已公开"**不自行维护第二套状态**，由前端用公开档案数据（`/records.json`）里的编号集合判断；内部状态仍沿用现有审核含义（"初审通过"= 用户的"整理中"，不等于已发布）。
- 撤回：尚未转入档案草稿的投稿，撤回后回到**草稿**（可继续编辑、重新提交）；已转入草稿的沿用现有"停止处理申请"机制，由站主核查。

## 三、数据模型扩展

投稿的唯一真实来源仍是 `submissions.mjs` 的私密收件区（`record.json` + 图片副本）。阶段三只**增加字段**，不改变既有结构，旧记录读取时补默认值：

| 字段 | 含义 |
| --- | --- |
| `account_id` | 归属账号；`null` 表示免注册投稿 |
| `status` | 新增 `draft`（草稿） |
| `versions` | 内容版本快照数组：`{ revision, at, action, fields, images, fingerprint }`，最多保留最近 20 个 |
| `change_request` | 已公开投稿的修改或撤下申请：`{ at, kind, note, status }` |

账户投稿的字段（`fields`）比免注册投稿多三项、少两项：新增 `place`（大致地点）、`source_note`（来源与展示授权依据）、每张图片的 `note`（单张说明）；**不再要求** `name`/`contact_type`/`contact`（方案 J：登录用户不重复填写私密联系方式）。

账号侧只增加一个**索引表**（`submission_index`：`id`、`user_id`、`status_cache`、`updated_at`），用于按账号列出投稿；状态以 `record.json` 为准，索引只用于排序与筛选，不作为真实来源。

## 四、接口定义

### 账户投稿（`/api/account/submissions/*`，需登录）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/account/submissions` | 本人投稿列表（含用户可见状态与待处理数量） |
| POST | `/api/account/submissions` | 新建：`mode = draft \| pending` |
| GET | `/api/account/submissions/:id` | 详情：字段、图片、站主说明、处理记录、版本数 |
| POST | `/api/account/submissions/:id/save` | 保存草稿（可增删图片） |
| POST | `/api/account/submissions/:id/submit` | 提交审核（生成只读版本） |
| POST | `/api/account/submissions/:id/withdraw` | 撤回（未转草稿时回到草稿状态） |
| POST | `/api/account/submissions/:id/request` | 已公开投稿的修改 / 撤下申请 |
| GET | `/api/account/submissions/:id/images/:filename` | 读取本人投稿的图片 |
| POST | `/api/account/submissions/claim` | 关联旧投稿（账号 + 编号 + 原密钥 + 明确确认） |

### 管理接口（沿用 `/api/admin/submissions/*`）

- 列表与详情增加 `account_id` 与账号信息（昵称、账号状态），用于识别账号投稿；
- 审核保存时的"给投稿人的说明"保持不变，账号投稿人与免注册投稿人都能看到；
- 审核动作触发进度通知（仅当该账号主动开启通知偏好）。

## 五、通知与失败处理

- 通知在以下时点触发：待补充、初审通过（整理中）、暂不采用、正式发布成功、撤下处理结果。
- 只在该账号 `notify_progress = 1` 时发送；发送失败记入 `mail_events`，**不影响审核结果**，也不重复执行发布。
- 邮件只写"有新的处理结果，请登录查看"，不附图片、投稿正文或联系方式。
- 上传部分失败时保留已成功保存的内容，失败图片单独重试；保存失败不得显示"已保存"。

## 六、验收办法（对应方案 N）

1. 用虚构资料走通"投稿 → 待补充 → 重提 → 初审 → 转草稿 → 人工发布检查 → 成功公开"，每一阶段公开状态真实准确。
2. 草稿跨设备恢复；断网、重复点击、多窗口编辑不静默丢失、不重复投稿、不覆盖已审核版本。
3. 用户 A 不能读、改、删用户 B 的草稿、投稿、图片与申请。
4. 旧投稿关联必须账号 + 原编号 + 原密钥三者同时正确；仅凭相同邮箱或相似图片不能认领。
5. 通知只在用户开启时发送；邮件失败不丢投稿、不重复发布。
6. 私密投稿数据不进入 `site/dist/`、站点地图与公共缓存；既有免注册投稿、回执、联系、纠错、搜索、点赞、足迹与管理流程无回归。
7. 全部既有测试与 `site/` 正式 `npm run build` 通过。

## 七、已知限制

- 已公开投稿的"修改"申请由站主人工处理：系统负责记录申请、在两侧可见；自动生成替换草稿仍由站主在管理端操作。
- 版本快照保留最近 20 个，超出后最旧的自动淘汰（图片本身不删除）。
- 通知依赖邮件通道；通道未配置时会在账号设置中明确说明，不会假装已发送。
