## 一、本阶段完成内容

方案 M 对阶段三的定义是"实现草稿、上传、版本、进度、补充、旧投稿关联、通知和最小管理扩展；打通原有私密收件、inbox、档案草稿、审核和发布流程"，并要求"用虚构资料演练成功、失败与恢复全过程"。

| 功能点 | 实现情况 |
| --- | --- |
| 草稿 | 可保存不完整内容、跨设备继续；未提交草稿与已提交投稿分开；离开页面前提醒 |
| 上传 | 本地预览后才上传；1—8 张、每张 ≤ 5 MB、合计 ≤ 20 MB；顺序可调、可移除；部分失败可重试 |
| 版本 | 提交时留下只读版本快照（保留最近 20 个）；提交后不能再按草稿编辑；修订号冲突拒绝覆盖 |
| 进度 | 用户可见状态由内部状态映射；"已公开"用公开档案数据判断，不维护第二套状态 |
| 补充 | 待补充状态在详情页看到站主说明，可继续编辑并重新提交 |
| 旧投稿关联 | 必须同时提供已登录账号 + 原投稿编号 + 原查询密钥，并主动勾选确认 |
| 通知 | 只在用户主动开启通知偏好时发送；邮件只写结果，不含图片、正文或联系方式 |
| 最小管理扩展 | 审核端区分账号投稿与免注册投稿、显示账号昵称与状态、发送可见处理说明 |
| 打通既有流程 | 沿用同一个私密收件区、同一套人工隐私检查、同一个转草稿与发布门禁 |

### 怎么打开

1. 双击项目根目录的 `启动档案管理.cmd`；
2. 投稿人侧：`http://127.0.0.1:4173/me/contributions/`（我的投稿，含"上传档案"与旧投稿关联），`/me/contribution/`（投稿工作台）；
3. 站主侧：`http://127.0.0.1:4173/admin/submissions.html`（筛选项新增"账号投稿"与"草稿（未提交）"）；
4. 本地默认使用本机私密投递通道，通知邮件会写入 `local-admin/accounts/mail-outbox/`，可直接查看。

## 四、数据模型与接口概要

投稿的唯一真实来源仍是私密收件区的 `record.json`。本阶段只**增加**字段，旧记录读取时补默认值：`account_id`、`status = draft`、`versions`、`change_request`。账号侧只增加 `_account-index.json`（账号 → 投稿编号）作为列表索引，不存状态。

账户投稿接口（`/api/account/submissions/*`，需登录）：`GET 列表`、`POST 新建`（草稿或直接提交）、`GET 详情`、`POST :id/save`、`POST :id/submit`、`POST :id/withdraw`、`POST :id/discard`、`POST :id/request`、`GET :id/images/:filename`、`POST claim`。

安全约定：全部接口要求登录会话与 `X-LJM-Account-Request` 标记；不属于当前账号的投稿、图片与申请统一返回"找不到"，避免泄漏编号是否存在；图片响应为 `no-store`。

### 端到端验证发现并修复的两个问题

1. **隐私缺陷（已修复）**：账户详情最初直接复用了管理端的详情结构，会把管理员的内部备注与含内部备注的处理记录下发给投稿人。已改为剥离 `private_note`、`key_hash`、`fingerprint` 及内部历史后再返回，并复测确认不再泄漏。
2. **版本混用（已修复）**：投稿的发布授权条款版本与账号协议版本是两套（方案 E 明确要求"发布授权在每件投稿中另行确认，不能用注册协议替代"）。工作台原先误用账号协议版本，导致提交被拒；现已分别获取，提交恢复正常。

## 六、已知限制与未做

- **线上部署未做**：独立账户进程的服务器数据目录、Caddy 路由与反向代理只转发 `/api/account/` 前缀的形态，均属阶段四授权范围。
- **邮件服务尚未配置**：通知与验证码都依赖邮件通道；通道未配置时界面会明确说明，不会假装已发送。
- **已公开内容的修改申请为人工受理**：系统负责记录申请、在两侧可见、阻止继续发布；用新草稿替换公开版本仍由站主在管理端操作。
- **前端核对以静态与接口验证为主**：本阶段未做浏览器自动化的逐像素核对；建议你实际点一遍"上传档案 → 保存草稿 → 提交审核"的完整流程。
- **未做**：评论、私信、公开个人主页、批量导入、AI 识别（总方案已排除）；阶段四的上线前验收与有限开放。
