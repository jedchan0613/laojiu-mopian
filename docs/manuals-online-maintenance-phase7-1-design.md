配套文件：[开发阶段计划](manuals-development-plan.md)、[第7阶段验收清单](manuals-online-maintenance-phase7-acceptance.md)、[原本地维护验收](manuals-phase3-review.md)。

## 一、目标与范围

目标是在现有受保护的管理员网站中，点击“说明书维护”即可整理品牌、准确型号和说明书目录，完成“保存草稿 → 预览 → 发布前检查 → 人工确认 → 正式发布”，并支持撤下和从历史恢复草稿。

| 内容 | 第7阶段的处理方式 |
| --- | --- |
| 品牌、型号、说明书版本、官方来源 | 复用已有编辑器和字段，接通线上保存 |
| 站内阅读、页序和目录 | 只关联已审核并公开的档案附件，增加适用于管理域名的预览 |
| 草稿、预览、检查、发布、撤下、历史恢复 | 纳入本阶段的完整维护流程 |
| 新图片及真实藏品入站 | 沿用原档案管理、待入站、隐私和人工批准流程；说明书页只引用发布副本 |
| 说明书投稿专用审核、转入整理草稿 | 保持独立的本机限制，列为后续单独任务；本阶段补清楚线上提示和入口状态 |
| 已有投稿来源绑定 | 继续保留并校验，不能手工伪造审核结果或解除停止处理限制 |
| PDF上传、生成、送审及最终开放 | 不随目录维护开放；继续使用独立开关与独立授权 |
| 账号、邮件、收藏、原始档案主库 | 本阶段不改动业务规则或数据结构 |

第7阶段复用现有Node管理服务、JSON目录、写入协调器、Cloudflare Access管理员登录和静态网站发布器。不新增Node包、数据库、CMS、后台服务、公开端口或云产品；维护成本主要是一个功能开关、目录历史及既有发布检查。

## 二、现状与必须解决的问题

本次阅读了当前工作目录和上次发布代码副本。发布副本记录为a80cb8f文档提交，其功能代码对应6.6最终部署9f555d2。本轮未连接服务器；这里的路径和部署标记是设计基线，7.5必须重新盘点实际情况。

| 已核实的代码行为 | 对线上接入的影响 |
| --- | --- |
| `server.mjs`在`onlineMode`下拒绝`/api/manuals`和`/admin/manuals*` | 不能只显示菜单或直接删除限制，需要先具备安全的线上维护流程 |

| 当前目录事务执行构建，未调用线上`releaseDeployer` | 仅构建成功不等于公开网站已经采用新目录 |
| 当前事务复制整个旧`site/dist`作为本机回退副本 | 线上应利用已有不可变公开版本回退，避免每次维护重复备份整站 |

| 维护页和预览页中的`/manuals/`、`/archive/...`使用相对链接 | 在独立管理域名上可能指向不存在的页面或图片 |

| 说明书专用审核有另一组本机限制，健康能力值在线上为0 | 开放维护不能顺带宣称投稿审核和PDF交接已开放 |
| 通用部署锁的现有封装受合并功能开关控制 | 说明书发布必须独立取得同一把部署锁，不能依赖合并是否开启 |

## 三、入口、权限和开关

### 3.1 沿用现有管理员身份

管理服务继续只监听`127.0.0.1`，由现有管理域名和Tunnel访问。管理页、接口、预览和图片均须经过既有Access签名、有效期、audience和管理员邮箱名单核验。普通网站账号不获得维护权限。

保存、检查、发布、撤下和恢复继续验证管理域名来源、JSON类型、管理请求标记和请求大小。维护写入沿用操作编号、步骤编号和目录版本，防止其他网页触发操作及旧页面覆盖新资料。服务器记录经过验证的管理员身份，不能采用浏览器自行填写的“审核人”。身份只进入私密事务和历史记录。

### 3.2 增加一个独立的线上维护开关

拟新增`LJM_MANUALS_ONLINE_ENABLED`，线上默认`false`；本机既有维护能力保持原规则。它与`LJM_ACCOUNT_PDF_OPEN`、合并开关分别判断。只有7.3完整发布流程已接通、7.4通过、7.5明确授权后，才在服务器设为`true`。

开关拟放在仅管理员服务读取的非密钥配置中；可采用`/etc/laojiumopian-manuals.conf`及现有管理员服务的最小配置追加文件。具体文件名、读取顺序和实际生效值在7.5核对，不整份改写含邮件或登录密钥的环境文件，不修改系统安全策略。

配置检查与实际服务须采用同一读取链。部署锁的文件权限及服务可写范围也要在Linux实测；若需要最小服务配置调整，先列入7.5的具体上线清单，不能放宽整个系统或私密目录的保护。

服务使用同一处判断生成路由开关、`/healthz`能力和受保护的工作台能力信息。拟在`/api/bootstrap`增加`capabilities.manualsMaintenanceVersion`，与健康接口同值：本机或已正式启用的完整线上实现为1，未开放为0。既有`manualReviewVersion`、`manualPdfHandoffVersion`在线上继续为0。

维护能力与当前可写状态分开：能力已开放，但资料未初始化或存在中断事务时，维护页应解释原因并只读，不能把“支持此功能”当作“任何时候都可发布”。每次写入仍重新核对状态。

### 3.3 菜单与错误页面

1. 桌面和手机入口默认隐藏；读取到明确维护能力后才显示。旧服务缺少能力字段时保持隐藏。
2. 为维护入口设置明确的隐藏样式，并在浏览器核对最终显示状态，覆盖现有`display:grid`影响。
3. 未开放时，已登录管理员直接访问维护页面，得到中文说明及“返回档案管理”；接口保留带稳定错误代码的JSON和404状态。未经身份验证的访问继续由原登录保护处理。
4. 已开放时，维护页显示“线上维护”；依据、审核备注改称“仅管理端可见”。“正式发布”和“撤下”明确影响公开说明书库；本机模式继续显示本机文案。
5. 投稿收件箱检测专用审核能力。能力为0时，显示“此投稿需在本机专用审核入口处理”，不提供一个必然失败的线上审核按钮。

### 3.4 页面和接口清单

下列维护入口都在现有管理员身份和维护开关之后，不增加公开网站代理。工作台新增能力字段同时覆盖当前使用的`split-v1`响应；健康接口只继续返回能力版本，不返回目录、私密状态或身份。

| 方法与地址 | 用途 | 写入及阶段 |
| --- | --- | --- |
| `GET /admin/manuals.html`及其JS/CSS | 维护页，按模式和就绪状态显示 | 7.2；页面本身不写资料 |
| `GET /api/manuals` | 已发布目录、独立草稿、历史摘要、可选公开档案和维护状态 | 7.2；不因读取自动建立空状态 |
| `POST /api/manuals/save` | 保存整个目录草稿，校验版本及来源绑定 | 7.2；不改变公开版 |
| `GET /admin/manuals-preview.html`及其脚本 | 已保存资料的预览界面 | 7.2；只读 |
| `GET /api/manuals/preview` | 按manual和revision生成预览数据 | 7.2；只读 |
| `GET /api/manuals/preview-image` | 按同一版本和页序读取正式发布副本 | 7.2新增；只读 |
| `POST /api/manuals/review` | 发布前检查，生成短期检查凭据；不是投稿专用审核 | 7.3；不改变公开版 |

## 四、保存位置、升级和首次初始化

### 4.1 资料分层

| 资料 | 位置与用途 | 对外范围 |
| --- | --- | --- |
| 线上正式目录及独立草稿 | `${LJM_ADMIN_DATA_ROOT}/manuals/state.json`；设计基线为`/srv/laojiumopian-admin/data/manuals/state.json` | 私密 |
| 草稿修改前、发布前、撤下前历史 | 同目录`history/` | 私密；恢复只生成草稿 |
| 发布事务、前后目录、发布版本引用 | 同目录`transactions/` | 私密；用于核对和失败恢复 |
| 操作状态和回执 | 既有管理数据根下的`operations/` | 仅管理员查询 |
| 供网站构建的目录 | 当前候选网站`site/src/data/generated/manuals-catalog.json` | 仅含白名单公开字段 |
| 访客实际阅读的网站 | `/srv/laojiumopian/releases/<版本>/`，由`live`指向当前版 | 公开静态成品 |
| 扫描件与原始主档 | 继续保留在原档案系统；维护页面只引用已公开附件 | 不进入目录维护或公开部署包 |

继续使用版本1的品牌—型号—文档目录结构，保存整个目录，不在本阶段改成逐条数据库。多值字段保持数组。草稿允许缺项，发布检查仍核对准确型号、来源、权利、隐私、页序、缺页和关联档案状态。

沿用现有请求大小限制，并在保存或发布前核对必要磁盘余量；空间不足时明确拒绝，保留已有资料。历史增长纳入维护盘点，不新增自动删除历史或图片的规则。

私密目录不得位于网站源码、`site/dist`或公开版本中，不接受链接到其他位置。沿用管理服务身份及受限目录权限；历史、依据、联系方式、来源绑定、操作人和源PDF均不进入公开投影。真实入站继续执行[入站流程](intake-sop.md)和[隐私检查](privacy-checklist.md)。

### 4.2 首次开放前的四种状态

| 盘点结果 | 处理方式 |
| --- | --- |
| 私密状态有效、无未决事务，公开投影可核对 | 沿用私密状态；按同一档案快照比较其公开投影 |
| 私密状态缺失，已明确确认没有既有正式条目 | 记录空基线后，才允许初始化空状态；首次保存前也执行该检查 |
| 私密状态缺失，但已有正式条目 | 禁止空初始化、整目录覆盖或从公开字段补造审核依据；先受控恢复并核验完整私密维护记录。找不到记录时保留原公开版，单独整理迁移方案 |
| 状态损坏、差异无法解释、链接异常或有未决事务 | 保留现状、显示待核对原因并阻止相关写入，不自动猜测或重放 |

本机空目录和演示样例不能证明服务器没有真实条目。初始化、恢复或迁移要记录来源、条目数、摘要、操作者和前后状态；不能把“曾经公开”转换为“现在已经重新人工确认”。

### 4.3 日常升级

程序版本目录仍只包含代码和公开输入，私密目录固定保存在`LJM_ADMIN_DATA_ROOT`，不随版本清理。自动部署在同一部署锁下，以正式`published`目录生成候选公开投影；`draft`不得参与网站构建。没有私密记录时继续核验并保留旧公开投影，不能因此生成空目录。

自动部署需要识别未决说明书事务；未决状态未核清前，不得通过代码升级绕过暂停状态。运行服务、配置检查和部署同步必须使用明确的数据根及候选`LJM_SITE_DIR`，避免写入旧版本或另一套目录。

## 五、预览与跨域名链接

保存草稿后，从`/admin/manuals-preview.html?manual=...&revision=...`进入受保护预览。预览绑定目录版本；草稿更新或档案不再符合公开条件时，旧预览失效，并提示返回重新打开。

“查看说明书库”和“查看已公开原档案”由服务器已核验的`PUBLIC_SITE_URL`生成完整网址，不能用管理域名下的相对公开路径，也不能接受浏览器任意指定跳转域名。

拟新增同域图片接口：`GET /api/manuals/preview-image?manual=<标识>&revision=<摘要>&page=<页序>`。服务器根据当前目录、关联档案和页序确定图片，不接受任意路径或外部网址。仅返回本档案正式附件列表中的已公开发布副本，检查ACT/G/U3、对象类型、schema、图片类型和路径；图片来源固定为网站发布副本目录，不回退到待入站区、回收区或源PDF。

预览数据中的图片地址只在管理端响应中转换，公开目录格式保持原样。页面、JSON和图片采用`no-store`，沿用同域图片限制；不扩大CSP、CORS或公开网站路由。官方来源仍由维护者实际核对，服务器不因保存网址而自动抓取外部文件。

## 六、线上发布、撤下和恢复

### 6.1 一次发布的顺序

1. 接收已保存目录版本及有效检查凭据；按原规则逐项完成人工确认，展示整个目录的新增、修改和移除影响。
2. 取得与Git自动部署共用的文件锁，再进入管理写入队列；记录操作编号、管理员身份、目录及附件摘要、旧状态、旧公开输入和当前`live`版本。确认磁盘余量和旧版本可用于回退。
3. 在候选构建目录生成白名单公开输入，执行现有正式`npm run build`及公开成品检查。访客继续读取旧的不可变公开版本。
4. 复查目录版本、关联档案、附件、投稿停止处理及已有审核来源绑定。使用既有发布器准备新的公开版本，采用`retain:true`和`onPrepared`记录新版本；切换前再次检查数据未变、锁仍持有且`live`仍为记录的旧版本。
5. 在切换前写入事务阶段，再原子切换`live`。完成正式目录状态和事务记录的落盘，并生成包含目录版本及公开版本标识的回执。所有步骤核对通过后，界面才显示“已正式发布”。
6. 发布成功后按原版本保留规则处理构建产物；任何仍被未决事务引用的旧版或候选版必须受保护。整理失败作为维护提示，不把已成功的发布错误重做。

现有目录事务需要增加线上发布适配，将“构建”“切换公开版本”“保存已发布状态”放入同一可恢复流程；不能在现有发布函数结束后额外调用一次部署并立即宣称成功。新版本切换后的状态落盘失败同样属于需要恢复或核对的事务。

### 6.2 锁、重复请求和长构建

使用已有`/run/lock/laojiumopian-github-deploy.lock`及`acquireDeploymentLock()`，线上说明书操作不以合并功能开关决定是否加锁。所有可能改动共用构建输入或切换公开版本的管理员路径都应核对锁覆盖，固定顺序为“部署锁 → 管理写入队列”，避免互相等待。Git部署已经在父进程持有此锁时，内部同步命令不得再次取得同一把锁。

继续使用现有操作协调器和`GET /api/operations/<操作编号>`查询结果。一个待核对请求保持相同操作及步骤编号；浏览器超时、刷新或短暂断网后先查回执，不换新编号重复发布。只持久保存待核对编号，不在浏览器额外长期保存完整目录、凭据或私密依据。

构建中允许查看进度及请求停止，但实际停止以服务端回执为准。切换前取消应回退；已经切换后不再把浏览器断开当作取消。进程退出、锁丢失或结果未知时显示“需核对”，不自动续发。继续复用当前进程与操作记录，不增加任务服务。

### 6.3 失败与中断

| 故障位置 | 处理要求 |
| --- | --- |
| 检查不通过或尚未改变任何资料 | 明确列出问题，公开版保持原状 |
| 构建失败、准备新公开版失败或切换前资料变化 | 恢复旧公开输入及正式状态，保留原草稿和诊断；`live`不变 |
| 切换后保存状态或记录失败 | 在锁仍有效且`live`仍指向本次候选的条件下恢复旧指针，再恢复状态；失败则保留前后材料并暂停相关发布 |
| 断电、进程中断或回执写入失败 | 启动后核对事务、实际`live`和目录摘要。只读查看可用；相关写入、同步和版本清理暂停，不能仅凭浏览器报错判定未发布 |
| 实际`live`不是记录的旧版或本次候选 | 不覆盖其他版本；停止自动恢复，交由维护者核对 |

在线上回退时引用已经保留的旧公开版本，事务主要保存必要JSON、摘要和版本位置，不逐次复制整个旧网站。本机既有回退分支保持原有含义；历史恢复仍然只是恢复目录草稿，不能声称永久保存了每个历史网站成品。

### 6.4 撤下和恢复

撤下继续要求填写原因、查看影响并确认，走同一构建、切换和回退流程；成功后公开目录、查询索引和阅读入口一起更新，原档案及图片不删除。撤下目录引用不等于撤下原档案。

恢复历史前保存当前草稿，只生成新草稿；重新检查、人工确认和发布后才对外生效。关联档案撤下、隐私或权利变化后，旧确认不能复用。已有投稿或PDF来源绑定继续由原规则校验，不能因审核入口暂未线上开放而绕过。
