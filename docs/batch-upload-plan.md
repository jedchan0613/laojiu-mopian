# 藏品批量自动化上传方案（草案）

> 目标：用脚本/Agent 工作流替代在档案管理前端逐件手动填写、逐张上传的操作。
> 编写日期：2026-10-12。本文档仅为方案，尚未实施任何代码改动。

---

## 0. 先说结论

现有管理系统**本身就是一套 HTTP 接口**（本机 `127.0.0.1:4173`），前端页面只是这些接口的"壳"。
因此批量上传**不需要新开发服务端功能**，也不需要绕过任何校验——写一个批量脚本，像浏览器一样依次调用
`/api/stage-image`（传图片）→ `/api/save-draft`（存草稿）→（人工确认后）`/api/publish`（发布）即可。

推荐采用**两段式**：机器批量做到"草稿"为止 → 人在管理界面逐件核对、勾选 13 项隐私检查后发布。
这既符合 `AGENTS.md` 和入站 SOP 中"敏感判断必须人工"的硬性要求，也把 90% 的重复劳动交给了机器。

---

## 1. 整体实现思路（三种方案对比）

### 方案 A：HTTP 脚本直连管理接口（推荐）

- 做法：一个 Node.js 脚本（用 Node 内置 `fetch`，零新增依赖），读取 Excel/CSV 清单 + 图片文件夹，循环调用管理接口。
- 前提：本地管理服务已启动（`启动档案管理.cmd`），脚本设置两个固定请求头：
  - `Origin: http://127.0.0.1:4173`
  - `X-LJM-Admin-Request: 1`
- 优点：
  - 完全复用现有全部校验（图片魔数、SHA-256 校验、字段完整性、编号自动分配、草稿/历史/回收区机制）；
  - 本地模式无需登录认证，脚本写法简单；
  - 与管理前端看到的是同一份数据，草稿会出现在管理界面里，人可接着核对。
- 缺点：脚本需在本机运行、且管理服务处于启动状态（对日常使用不是障碍）。

### 方案 B：账户投稿接口（/api/account/submissions/*）

- 做法：模拟登录账户，走投稿通道批量提交。
- **明确不推荐**，原因：
  1. 需要邮箱验证码登录拿 session，自动化要多一套取码流程；
  2. 有硬性配额：每天提交审核 ≤10 件、草稿 ≤20 件、合计 ≤200MB、单批 ≤8 张图——天生就是"防批量"的；
  3. 投稿走的是"管理员审核后转入草稿"的另一条链路，等于给自己增加一道无意义的中转。

### 方案 C：Agent 浏览器自动化（模拟人点页面）

- 做法：用浏览器自动化驱动现有管理前端，逐件填表、点上传。
- 不推荐作为正式路径：速度慢、易受页面结构变化影响、失败原因难诊断；本质上是把方案 A 包了一层易碎的壳。
- 仅在"接口暂时不能满足、又不想改服务端"的过渡期可考虑。

**结论：选方案 A。** 方案 C 可作为零代码量的临时兜底，方案 B 排除。

## 2. 数据准备（模板与目录约定）

### 2.1 清单文件：一份 Excel/CSV（建议 CSV，UTF-8，避免 Excel 软件差异）

每行 = 一件（套）藏品。字段分三组，与 `archive-data/metadata-template.json` 三层结构一一对应：

**A. 通用层 core（必填）**

| 列名 | 说明 | 示例 |
|---|---|---|
| accession_date | 接收/获得日期，决定永久编号 | 2026-10-12 |
| object_type | 类型代码 | PHO / PST / CRD / IDN / DNB … |
| title | 标题 | 上海街景明信片 |
| date_display | 显示年代（无法判断填"年代未知"） | 1930年代 |
| rights_status / evidence_level / research_status | 按代码字典填 | 以 `04_代码字典` 为准 |
| evidence_basis | 证据依据（多值用英文分号） | 原件;背面题记 |

**B. 专属层 metadata**

| 列名 | 说明 |
|---|---|
| schema | photo / postcard / diary_notebook / credential / card / common |
| 其余列 | 按各类型 D01–D21 / PC01–PC21 等维度各设一列；多值字段用英文分号分隔，脚本转成数组 |

**C. 展示层 public_view 与图片**

| 列名 | 说明 |
|---|---|
| description / transcription | 公开描述、转录文字 |
| tags | 英文分号分隔 |
| image_folder | 该件图片所在子文件夹名（见 2.2） |

永久编号 `item_id` **不填**，由服务端按 `LJM-YYYYMMDD-TYP-NNN` 自动分配，避免人工编号冲突。

### 2.2 图片组织方式

```
batch-inbox/                      # 批量源目录（位置自定，在项目外或单独目录均可）
  batch-2026-10.csv               # 清单
  images/
    001/                          # 与清单 image_folder 列对应
      front.jpg                   # 正面（命名约定见下）
      back.jpg                    # 背面
      detail-01.jpg               # 细节图，可多张
    002/
      front.jpg
```

- 图片必须是**已脱敏、压缩好的发布副本**（JPEG/PNG/WebP，单张 ≤30MB），脚本不做脱敏；
- 命名约定：`front` → `front-public.jpg`，`back` → `back-public.jpg`，`detail-NN` → `detail-NN-public.jpg`，与现有管理系统的自动命名完全一致；
- 文件名不得含 master/original/raw/主档/原始 等字样（沿用现有约束）。

## 3. 批量上传流程（完整步骤）

```
读清单 → 逐行校验（预检）→ 逐件上传图片 → 逐件存草稿 → 生成对账报告
                                                    ↓
                            人在管理界面核对 → 勾选13项隐私检查 → 逐件/分批发布
```

**第 1 步：读取与预检（dry-run，不落盘）**
- 解析 CSV，校验：必填列齐全、代码值在代码字典内、object_type 与 schema 匹配、
  图片文件夹存在且命名合规、单张 ≤30MB；
- 预检产出一份"预检报告"，任何一行不合格则该行标记为跳过，不影响其他行。

**第 2 步：逐张上传图片**
- 对每件藏品的每张图：计算 SHA-256，`POST /api/stage-image`（二进制直传，带
  `X-LJM-File-Name`、`X-LJM-File-SHA256` 头），拿回 `uploadToken`。

**第 3 步：逐件保存草稿**
- `POST /api/save-draft`，body 中 `images` 全部使用 `{"kind":"staged","uploadToken":"..."}`；
- 成功则图片自动落入 `public-assets/inbox/<新分配的item_id>/`，草稿出现在管理界面。

**第 4 步：结果反馈**
- 脚本输出对账报告（CSV + 控制台摘要）：每行对应 成功(新编号) / 跳过(原因) / 失败(错误信息)；
- 报告回写一份 `batch-result-YYYYMMDD-HHMM.csv` 到批量源目录，方便人工核对。

**第 5 步：人工核对与发布（保留人工门禁）**
- 人在管理界面逐件打开草稿核对，勾选 13 项隐私检查后点发布（现有功能不变）；
- **注意**：现有 `/api/publish` 每发一件就全站构建一次。批量件数较多时（如 >10 件），
  建议后续增加一个"批量发布"小改动（多件共用一次构建），但这属于单独授权的服务端改动，
  第一阶段不改动，先接受"逐件发布、逐件构建"。

## 4. 异常处理（重试与回滚）

| 场景 | 机制 |
|---|---|
| 图片上传失败/网络中断 | `/api/stage-image` 天然幂等（同一文件 SHA-256 不变），直接重试同一张即可；单张重试 ≤3 次，仍失败则该件整体标记失败，进入下一件 |
| save-draft 失败 | 已暂存的图片在 `upload-staging/` 有过期清理；草稿未落盘 = 没有副作用，修正数据后重跑该行 |
| 中途整个脚本中断 | **断点续跑**：脚本在源目录维护 `batch-progress.json`，记录每行状态（pending/staged/drafted/failed + uploadToken）；重跑时跳过已完成行，staged 状态的 token 若已过期则重传图片 |
| 编号重复/冲突 | 编号由服务端原子分配，不存在脚本侧冲突 |
| 发布阶段失败 | 沿用现有 `/api/publish` 的自动回滚（构建失败自动还原），不新增风险 |
| 错误数据已进草稿 | 草稿可在管理界面直接改或删；删除草稿走现有回收区机制，图片不丢失 |
| 敏感内容 | 脚本不做任何隐私判断；凡涉及证件号、电话、地址、可识别人物等，一律在清单阶段留给人——脚本只负责搬运，第 5 步人工核对是不可跳过的闸门 |

**回滚原则**：批量脚本的作用范围止于"草稿"，不直接碰已发布数据，因此不需要复杂的回滚机制；
万一草稿批量出错，删除对应草稿（走回收区）即可恢复原状。

## 5. 前置条件

1. **环境**：本机 Node.js（现有 v22 即可，零新增 npm 依赖，只用内置 `fetch`/`fs`/`crypto`）；
2. **服务**：本地管理服务已启动（`启动档案管理.cmd`，监听 `127.0.0.1:4173`）；
3. **权限/认证**：本地模式无账号体系，脚本只需带两个固定头（`Origin` + `X-LJM-Admin-Request: 1`）。
   此通道只监听本机回环地址，外部无法访问，安全边界与现有管理前端相同；
4. **数据**：发布副本图片已完成脱敏与压缩（脚本不负责脱敏）；
5. **规范**：清单中的代码值以 `docs/reference/archive-metadata-standard-v1.xlsx` 的代码字典为准。

## 6. 分步实施路径（建议）

| 步骤 | 内容 | 产出 | 预估性质 |
|---|---|---|---|
| ① 模板定稿 | 与你确认 CSV 模板列（哪些 metadata 维度常用、多值分隔符） | `docs/batch-upload-template.csv` 模板 | 纯文档，半天量级 |
| ② 预检脚本 | 只做读取+校验+预检报告，不碰接口 | `local-admin/batch/precheck.mjs` | 低风险 |
| ③ 上传脚本 | stage-image + save-draft + 断点续跑 + 对账报告 | `local-admin/batch/upload.mjs` | 核心工作量 |
| ④ 小批量试跑 | 用 3–5 件真实藏品走完整流程，人工核对后逐件发布 | 试跑记录 + 模板修正 | 验证环节 |
| ⑤（可选，单独授权） | 服务端增加"批量发布共用一次构建" | server.mjs 小改动 | 件数多时再评估 |

每一步完成并确认后再进入下一步；②③ 均为新增独立脚本文件，不改动任何现有代码。

## 附：关键接口速查（供实施时对照）

- `POST /api/stage-image`：二进制直传；头 `Content-Type: image/*`、`X-LJM-File-Name`（URL编码）、
  `X-LJM-File-SHA256`、`X-LJM-Admin-Request: 1`；返回 `{upload:{token,...}}`
- `POST /api/save-draft`：JSON；`{record:{core,metadata,public_view}, images:[{kind:"staged",uploadToken,...}], isNew:true, confirmedPublicationCopies:true, removedImages:[], removedImageDescriptions:{}}`
- `POST /api/publish`：JSON；`{itemId, confirmations:[true×13]}`（人工阶段使用）
- 相关源码：`local-admin/server.mjs`（save-draft 约 1653 行、publish 约 2171 行）
