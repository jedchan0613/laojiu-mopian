## 六、技术定案提案（供审阅，未实施）

### 1. 数据库：SQLite（首选 Node 内置 `node:sqlite`）

- **建议**：账号、会话、收藏、投稿归属保存在一个独立的 SQLite 文件，放在私密数据目录（如线上 `/srv/laojiumopian-admin/data/accounts/`）。本机 Node 24 已内置 `node:sqlite`，可以做到**零新增依赖**；服务器上的 Node 版本需要先核实，若不满足再评估升级或改用 `better-sqlite3`。
- **理由**：单文件、无需安装服务、备份简单，适合本站量级；写入用单进程串行即可满足。
- **维护成本**：低（一个文件）；**费用**：0。
- **退出办法**：数据可随时导出为标准 JSON/SQL 文件；将来迁移到 PostgreSQL 等需要另做适配，不做提前设计。
- **需要你配置**：无需配置软件，只需授权“建立账号数据库”这件事本身。

### 2. 认证组件：标准库原语 + 服务端会话，不引入第三方身份平台

- **验证码**：`node:crypto` 生成 6 位随机码；数据库只存不可逆摘要（带盐），比对用恒定时间比较；10 分钟有效、一次使用、最多 5 次尝试、60 秒重发防抖、重发即作废旧码。
- **会话**：服务端 `sessions` 表 + 256 位随机令牌，放在带 `HttpOnly`、`Secure`、`SameSite=Lax` 的 Cookie 中，可单独或全部撤销；闲置 7 天、最长 30 天，以服务器为准。
- **不引入** Auth0、Supabase 之类完整身份平台：会产生持续费用、外链依赖和数据出境问题，维护复杂度也更高；本站需求用标准库原语 + 成熟邮件服务即可覆盖（不设计自己的加密算法）。
- **维护成本**：中低；**费用**：0；**需要你配置**：无（除邮件服务）。

### 3. 邮件发送：从两个候选里实测后确定

| 候选 | 说明 | 备注 |
| --- | --- | --- |
| A. 专业邮件 API（如 Resend、SendGrid） | 用 HTTPS 接口发信，可以用 `fetch` 直连（零依赖），也可以配一个成熟库 | 海外服务，国内邮箱送达率需要实测 |
| B. 国内云邮件推送（阿里云 / 腾讯云） | 对国内常见邮箱送达率通常更稳 | 可能需要核实发送域名的备案要求；控制台配置项更多 |

- **预计费用**：按验证码与进度通知估算，每月不足 500 封，落在免费额度内约为 **0 元/月**；超出后按量计费，具体价格以服务商官网为准（实施前会重新核对）。
- **不推荐**直接用个人邮箱 SMTP 发验证码（送达率差、易被风控、密钥管理风险高），只作应急备选。
- **需要你配置**：在服务商注册账号、验证域名、在域名解析里加 SPF/DKIM/DMARC 记录（我会给出逐条说明）；密钥只放服务器环境文件，不进仓库。

### 4. 新增依赖：目标 0 个，最多 1 个

- 若邮件走 HTTPS API + `fetch`：**0 个新增依赖**（全部用 Node 内置能力）。
- 若必须用 SMTP：新增 1 个成熟库（如 `nodemailer`），随 `site/` 现有依赖一并维护和更新。
- 测试继续使用 `node --test`，不需要新工具。

### 5. 服务与部署隔离（本地与线上同一套边界）

- 新增独立的 `account-server.mjs`（暂定名）：**只监听 `127.0.0.1`**（本地如 4175、线上如 4177，最终以实施时的端口规划为准），只提供 `/api/account/*` 与账户页面所需接口；公开代理只转发这一前缀。
- 账户服务**不能**读写 `archive-data/`、`drafts/`、`history/`、`recycle-bin/`、`site/dist/`；它只读写自己的私密数据目录。
- 管理员与普通用户的接口、凭证、权限完全分开：普通账号不能通过改参数调用管理接口；管理端需要的账号信息（如投稿归属）通过本机内部接口读取，不把管理密钥交给公开进程。
- 公开接收进程（4176，投稿与联系）的权限边界保持现状，不扩大。

### 6. 数据流向

```text
访客 → 登录（邮箱验证码）→ 会话 Cookie（服务端可撤销）
   → 我的投稿 / 我的收藏 / 账户设置
   → 投稿（私密收件区，新增“归属账号”字段；图片处理与限流沿用现有逻辑）
   → 站主审核（现有审核区）→ 转未公开草稿 → 13 项隐私检查 → 正式构建 → 公开
收藏 = 账号 ↔ 永久档案编号 的关联表（默认私密）
公开网站始终只读取正式发布的档案数据，不读取任何账号数据
```

### 7. 备份与恢复

- SQLite 采用一致性备份（服务内快照或停写快照），与私密收件区、现有档案数据一起纳入现行备份流程；恢复演练纳入阶段四验收。
- 备份仍属私密资料；备份中不含明文验证码（本来就不存明文）、不含会话原始令牌（只存摘要）。

### 8. 保留与注销规则（草案，需你确认）

- **保留**：账号数据保留至注销；验证码记录只存必要字段并短期清理；会话到期自动失效。
- **注销**：人工受理；收到申请后立即撤销该账号全部会话、停止新投稿，并给出回执；申请页逐项展示“账户、私密投稿、公开署名、已公开内容、备份”的处理方式。
- **边界**：“撤下”“删除”“注销”是三件不同的事。注销不自动删除所有已公开档案；公开署名可以单独申请处理；不可逆清理需要你在具体场景下逐次授权，不永久删除已保存图片。
- **建议时限**：收到申请后 30 天内处理完成（需要你确认，作为对用户的公开承诺口径）。

### 9. 容量与限流（沿用方案 K，实施前按真实服务器再核一遍）

- 建议初始值：每天最多提交 10 件、同时最多保存 20 件未提交草稿、账号未公开资料合计不超过 200 MB。
- 按邮箱、来源地址和全站邮件额度共同限流；对用户只显示剩余额度和超限原因。

## 八、验收办法（对应方案 N，分阶段执行）

- **阶段二（账户、收藏与基础权益）**：隔离测试账号；跨用户越权检查（改编号、文件地址、请求参数、缓存）；验证码过期/重试/限流；退出全部设备的凭证撤销；邮件失败不丢数据；人工导出与注销申请打通。
- **阶段三（账户投稿与审核衔接）**：用虚构资料走通“投稿 → 待补充 → 重提 → 初审 → 转草稿 → 发布”；草稿跨设备恢复；断网、重复点击、多窗口编辑不静默丢失；旧投稿关联需要账号 + 原编号 + 原密钥三重确认。
- **阶段四（上线前验收）**：完整回归、正式构建、备份恢复演练、部署与回退清单、应急关闭开关；先小规模开放，再逐步扩大。
- **贯穿检查**：私密数据不进 `site/dist/`、站点地图、公共缓存与可公开读取的历史版本；现有免注册投稿、联系、纠错、搜索、点赞、足迹与管理流程无回归。
