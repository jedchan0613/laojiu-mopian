代码基线：`2418c7a`。生产静态检查固定到不可变版本 `/srv/laojiumopian/releases/20261018-093313-admin-1e12e325`，记录时间为北京时间09:41:42；维护期间内容可能继续变化，下面的译文数量属于该快照，不代表永久数量。

## 优先处理

### 1. 图片处理库有已公开安全告警，投稿入口实际使用它（高优先级）

- 本地锁文件和生产运行库均为 Sharp 0.35.3；生产附带 libheif 1.23.1、librsvg 2.62.90。Astro为7.2.7。
- `npm audit --omit=dev`报告8个受影响依赖包：1严重、6高、1中。它是包级汇总，不是8个已经成功利用的攻击入口。
- Sharp官方公告明确涉及恶意输入的原生图片处理风险。libheif问题修复范围为Sharp≥0.35.4，另一项librsvg问题要求≥0.35.5；因此不能只升级到0.35.4就认为本轮两个图片告警全部解决。Astro对应AVIF公告修复起点为7.2.8。
- `local-admin/submissions.mjs:76`的投稿处理先把上传字节交给Sharp，在第82行读取metadata，第83—84行才核对真实格式。只限制文件扩展名并不能阻止伪装成JPG的其他格式先被图片库读取。当前公开账户配置显示注册与上传均开启。这是代码路径与版本核对结论，未在生产上传恶意文件或尝试利用。
- 最小修复方向：在解码前核对允许格式的文件签名/限制不需要的解码器，更新现有依赖到覆盖相关公告的安全版本，并在Linux和Windows重新跑上传、发布、图片和完整构建回归。不要盲目执行强制依赖升级，也不需要引入新的云服务或框架。

依据：[Sharp libheif公告](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c)、[Sharp librsvg公告](https://github.com/lovell/sharp/security/advisories/GHSA-wq5f-xc86-pv6w)、[Astro AVIF公告](https://github.com/withastro/astro/security/advisories/GHSA-26w7-cxv4-gfx2)。

### 2. 档案详情页的嵌入文字数据漏了转义（高优先级）

- 位置：`site/src/pages/archive/[id].astro:719`，`record-view-data`直接将`JSON.stringify(recordViewData)`交给`set:html`；数据包含题名、图片说明等文字。
- 如果文字含有脚本结束标签，JSON字符串的引号不能阻止浏览器提前结束数据块，后续内容会被当作网页标记。这既能破坏浏览足迹，也形成存储型脚本注入风险；不是“所有访客输入都会自动公开”，真实发布仍有人工审核门禁。
- 已使用现有Astro编译器和渲染器做无害合成验证：未转义时首个数据块无法解析且后面出现额外HTML；转义`<`后数据能完整解析。没有执行注入脚本，没有写入真实资料。
- 搜索索引（`site/src/pages/archive/index.astro:94`）与结构化数据（`site/src/layouts/BaseLayout.astro:54`）已经做了这一步，详情足迹数据应统一采用同样的安全输出规则，并增加回归测试。

转义的含义是把特殊字符当普通文字输出，而不是让浏览器把它当网页代码。[Astro官方说明](https://docs.astro.build/en/reference/directives-reference/#sethtml)也明确要求使用`set:html`时保证输入安全。

### 3. 备份能否持续恢复，需要补齐确认与演练（重要待验，不是已证实无备份）

- 服务正常、旧程序版本可回退，不等于当前账号库、投稿图片和档案资料已经有可恢复的异地备份。
- 本次只读检查中，常规`backups/`目录只看到2026-09-03的阶段性备份；项目相关systemd计时器只看到部署检查，未确认定期全量备份任务。没有检查云服务商快照或所有其他私有目录，不能据此断言“完全没有备份”。
- 既有账号上线记录仍将账号数据库与私密收件区的一致备份/恢复演练列为待办。建议核对现行备份位置、频率、保留期限与离机副本，再在隔离目录恢复验证；不得用恢复测试覆盖生产数据。
