# 网站性能检查报告（2026-10-20）

本报告只做检查与测量，未修改任何页面、数据或配置。所有数字来自本机 `site/dist` 现有构建产物，以及构建后的 HTML/CSS 实际引用关系；未访问生产服务器，未做真机或浏览器交互测试。

## 一、总体结论

**存在一个严重的性能问题：中文字体下载失控。** 中文首页要额外下载约 2.2 MB 字体，中文档案目录页约 5.3 MB，日文档案目录页约 7.7 MB。这个问题比图片问题大得多，且会随档案数量增加而继续恶化。

除此之外没有发现会让页面打不开、白屏或卡死的问题。图片的响应式、懒加载、首屏优先级处理都是正确的；脚本总量只有约 86 KB，很小。

## 二、严重问题：中文字体按“生僻字”成片下载

### 2.1 现象

`site/src/layouts/BaseLayout.astro` 生成的 CSS 中一共有 **213 条** `@font-face` 规则，全部指向同一个字体族 `LJM Brand Serif`，分为两类：

| 类别 | 数量 | 体积 | 说明 |
| --- | --- | --- | --- |
| 手工精简子集 `base` / `extended` / `public-supplement` | 3 | 130 + 558 + 96 = 784 KB | 声明在最前面，优先命中 |
| 兜底分片 `full-0000` 至 `full-02f9` | 209 | 合计 12.3 MB，单片平均 60 KB、最大 202 KB | 声明在后面，主字体没覆盖到的字会落到这里 |

浏览器规则是：**同一个字体族、同一字重下，每个字符只用第一个覆盖它的那条规则**。所以主字体没覆盖的字，会去下载对应的一个 `full-*` 分片——而每个分片 60 KB 上下，往往只是为了渲染一两个生僻字。

### 2.2 实测数据

统计全站 HTML 可见字符共 **2796 种**，其中主字体（base + extended + supplement）覆盖不到的有 **1532 种**，这些字需要靠 **87 个** `full-*` 分片兜底，合计 **8.3 MB**。

按页面实测（按 CSS 首匹配规则推算）：

| 页面 | 会下载的字体文件数 | 字体体积 |
| --- | --- | --- |
| 中文首页 | 21 | 2275 KB |
| 中文档案目录页 | 52 | 5453 KB |
| 中文档案详情页 | 8 | 1031 KB |
| 英文首页 | 21 | 2196 KB |
| 日文首页 | 53 | 5797 KB |
| 日文档案目录页 | 72 | 7692 KB |
| 泰文档案目录页 | 27 | 3032 KB |

### 2.3 触发原因

主字体没覆盖、却被迫走兜底分片的字符，主要是：

- **每个页面都有**：语言切换器里的 `ไทย` `語` `한국어` `體` `✓`
- **档案正文/标题里的生僻字**：`砖 泥 浴 室 畔 座 壹 仟 肆 贰 柒 玖 漫 诊 乙 肝 疫 蚊 帐 炸 辫 筷 琴 蝴 蝶 …`

档案目录页字符最多，所以最重（79 个未覆盖字符触发 49 个分片，约 4.7 MB）。随着新档案入库，生僻字只会更多，这个数字会持续上涨。

### 2.4 影响程度

- 字体带 `font-display: swap`，文字会先用系统字体显示，**不会白屏**，所以“看起来能打开”。
- 但网络仍要实打实拉 2–7 MB。手机流量、弱网、按流量计费的访客成本很高；同时字体请求会和首屏图片抢带宽。
- 这是当前整站最大的单笔传输开销，比所有图片加起来还大。

### 2.5 修复方向（待确认，未执行）

优先级从高到低，三条可以叠加：

1. **重新生成主字体子集**：把 `base` / `extended` / `supplement` 按当前全站实际字符重新切一遍，让 1532 个未覆盖字进入主字体。这样 87 个兜底分片基本不再被触发，预计可从 2–7 MB 降到 0.8 MB 左右。
2. **删掉 209 个 `full-*` 兜底分片**：如果主字体已覆盖全站字符，这套 12.3 MB 的兜底就完全没用，可以从 CSS 和产物中移除（CSS 也会从 99 KB 瘦下来）。
3. **语言切换器改用系统字体**：`ไทย` `語` `한국어` 这类字符只出现在导航里，用系统字体渲染即可，不必让自定义字体去覆盖它们。这样每页少触发 3–4 个分片。

## 三、中等问题

### 3.1 三张二维码图片过大（每页 273 KB）

`public/social/` 下三张二维码是 `984×1470`、`987×1347`、`856×1211` 的 JPEG：

| 文件 | 尺寸 | 体积 |
| --- | --- | --- |
| `douyin-qr-public.jpg` | 984×1470 | 113 KB |
| `wechat-qr-public.jpg` | 856×1211 | 73 KB |
| `xiaohongshu-qr-public.jpg` | 987×1347 | 73 KB |

二维码是纯黑白块状图，按实际显示尺寸（约 300 px）转成 WebP 后单张只需几 KB。现在每页要多传 273 KB，且没有 `srcset`、没有 WebP。属于“白白多传”的量。

### 3.2 档案目录页偏重

- HTML 233 KB（gzip 34 KB），其中内联了 74 KB 的档案索引 JSON，用于客户端检索筛选。这个设计本身合理，但 HTML 会随档案数量线性增长。
- 卡片图：`sizes` 写的是 400 px，但候选宽度只有 320 / 640 / 1280。在 2 倍屏上需要 800 px，只能跳到 1280（平均 145 KB/张）；1 倍屏选 640（平均 44 KB/张）。**缺少 800w 这一档**，导致高分屏用户多下 2–3 倍。

### 3.3 构建产物 719 MB，其中 425 MB 是访客拿不到的原始图

- `site/dist` 总计 719 MB。
- `dist/archive/` 占 425 MB，324 张原始 JPEG，单张最大 10.42 MB。
- 检查确认：目前所有详情页的 `canDownloadPublicationCopy` 都是 false，**页面上没有任何“下载发布副本”入口**，访客实际下载不到这些大图。
- 也就是说这 425 MB 每次部署都要上传、都要占服务器磁盘，但对访客零收益。服务器此前已出现过磁盘空间不足导致部署回退，这一项与稳定性直接相关。

## 四、做得对的地方（无需改动）

- 响应式图片：`generate-responsive-images.mjs` 生成 320/640/1280/1920 四档 WebP，`srcset` + `sizes` 使用正确。
- 懒加载：首页 10 张图里 9 张 `loading="lazy"`；目录页 15 张里 14 张懒加载。
- 首屏优先级：首屏主图 `loading="eager"` + `fetchpriority="high"`，没有滥用预加载。
- 脚本体积：全部 JS 合计 85.6 KB（gzip 后更小），最大的单文件 16.6 KB，非常克制。
- 缓存策略：`_astro` 带内容哈希的资源一年强缓存，HTML `max-age=0, must-revalidate`，符合最佳实践。
- 字体回退：`font-display: swap` 保证文字不会因为字体没到而不显示。
- 没有音视频等重型媒体文件。

## 五、建议的处理顺序

| 顺序 | 事项 | 预期效果 | 风险 |
| --- | --- | --- | --- |
| 1 | 重新切分主字体子集 + 移除 `full-*` 兜底 | 首屏字体从 2.2–7.7 MB 降到约 0.8 MB | 需重新生成字体文件，改动 CSS 与产物；需回归检查六语言字形显示 |
| 2 | 二维码转 WebP 并缩小 | 每页少传约 260 KB | 极低，只换图 |
| 3 | 目录页补 800w 图片档位 | 高分屏卡片图少下约 60% | 低，改 `targetWidths` 后重新构建 |
| 4 | 清理 `dist/archive/` 中访客拿不到的原始图 | 部署体积从 719 MB 降到约 294 MB | 需确认“下载发布副本”未来是否启用；删除属不可逆操作，须单独授权 |

第 1 项是本轮唯一“严重”的问题，其余三项都属于优化，不改也不会影响网站正常使用。
