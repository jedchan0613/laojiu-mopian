# 档案合并功能：第二阶段实施与验收

日期：2026-10-24。用户先确认第一阶段“其它没问题”，提出重复保存问题并授权继续。对应主方案v2.1的第二步：**本机内部可恢复提交、全站基线、操作日志、旧号去向与统计验收**。本阶段没有变更生产档案、没有部署代码或调整服务器配置；通用线上合并和撤销合并仍未开放。

## 先修复重复保存

- 服务端比较有效内容摘要：主从编号、检查基础、各字段实际选值及理由、图片顺序、有效图注、不采用理由、同源和主件理由。对象键顺序、显式重复默认值、重复填写原图注、请求编号和保存时间不算内容改变。
- 同一方案重复保存不增加版本、不改变保存时间、不重写当前版和旧版本。未携带planId的新请求若与本人已有方案内容完全相同，也返回原方案。内容确有变化时才追加新版本；基础变化仍须明确重新核对，不能借去重绕过版本检查。
- 每个请求保留可找回的操作去向，返回 `saveUnchanged:true`；界面提示“内容没有变化，已保留原方案和版本，未重复创建”。这里去重的是方案及版本，不伪称网络请求从未发生。
- 浏览器在普通本机模式和内部验收模式分别连续保存三次，均只有一份方案、第1版；额外验证省略planId的相同请求仍归到同一方案。正常4173预览已重启到新代码，样例保持清晰的虚构标识。

## 本阶段实现

### 执行前重新核对

- 执行入口默认关闭，仅 `LJM_MERGE_INTERNAL_ENABLED=1` 且本机模式允许内部验收；线上模式不允许这些页面和接口，不因设置该变量而放行。
- 保存方案后重新申请30分钟核对令牌，绑定实际维护身份、方案版本、双方版本、图片、引用、收藏及全站输入。重启、超时、内容变化和不同维护身份均不能复用；普通重复保存不使相同内容新增版本。
- 使用现有构建器已有的Sharp进行真实完整解码，不安装依赖，不修改图片。校验最长边2000像素、单页、文件签名和摘要，存在EXIF/嵌入信息时退回另做副本和重新核对。损坏图片不会只凭文件头通过。
- 当前应用的发布副本必须与inbox同名副本摘要一致，受影响其他档案也须有完整来源，避免把新上传的同名图冒作“发布前快照”。不读取主档路径。
- 受影响正式档案已有草稿，或其他当前草稿含需要迁移的从件引用时阻断，不覆盖草稿、不暗改用户未发布的编辑。
- 私密投稿、未知引用、非零匿名点赞等不支持的情况仍阻断；未接入的借阅、审批、移交、保管期限与密级不会假装检查通过。界面的本人检查要求明确核对实际业务占用。

### 文件与关联提交

- 主件沿用永久编号；从件按现有字典保存WDR/U4正式撤销，原编号不回收。原JSON和图片分别保存独立、校验过的私密历史副本；不移动或删除原始主库，不对主档建立硬链接。
- 仅精确迁移已知结构化引用，去重并去自引用；不对转录或自由文字做全局编号替换。其他被修改的正式记录一并快照、核对版本。相册和主题仍由最终有效记录重建，影像数与档案件数分开。
- 新发布副本只能复制到空闲规范名，不能覆盖同名异内容。图片映射、来源页号、摘要、保留顺序及图注均入私密日志；不采用图片仍在inbox和历史中保留。
- 账号收藏复用已有账号SQLite，不另建档案数据库。仅在显式内部模式首次建立两张账号业务辅助表；旧库若已存在这些表，关闭开发入口后仍继续履行门禁和旧号解析。按用户合并双收藏，保留最早时间，不改变账号、会话或投稿所有权。
- 收藏提交采用短SQLite事务及持久化目标门禁，不在整个构建期间持写锁。迁移前后留证据；服务中断后仍拒绝对未核实目标写收藏。后续通过旧号新增或取消收藏，解析到主号。回退不能恢复已不存在的账号。
- 译文保持独立存储：主件原有译文保留为待复核稿，取消旧的公开审核状态并提高其维护版本；主从旧公开导出退出候选。原始私密版本保存在文件日志中，不自动拼接两份译文，不自动替所有人审核新组合。
- 匿名旧哈希包含档案编号，仍只支持目标0赞的情况。严格验证实际点赞服务的version/items/voters格式；异常格式不能当0。现有点赞服务和合并引擎使用同一短时文件写入门禁，忙时返回423，不等待抢锁、不清除未知归属。新点赞按当前公开摘要解析旧号到主号，同一访问者不会因使用旧入口多计一次。

### 候选构建、基线与失败恢复

1. 冻结正式记录、草稿、inbox、网站程序/字典/公共资源、私密译文、投稿、当前公开产物、程序代码、配置和锁文件摘要；收藏另有实际行摘要，点赞另有实际文件摘要。全站核对不只比较两件或引用数量。
2. 保存私密日志、双方及其他受影响记录的历史；在独立候选目录复制程序和发布副本，复用既有依赖目录。执行正式 `npm run build`，原公开版本仍保持原样。
3. 核对完整候选产物清单；最终提交前取得点赞与收藏写入门禁，再复查全站输入。写入期间继续核对“原基线＋本次允许变更”，第三件记录在临近提交时变化也不能被旧候选覆盖。
4. 先向当前本机应用写入副本、正式JSON、译文状态、公开生成源及图片映射，再切换本机dist。旧dist完整移入私密日志目录留存；未确认旧副本不会在候选阶段被移走。
5. 每个文件变更都先保存前后副本及摘要，再写入并更新阶段日志。切换前复核候选未被篡改，切换后核对全量允许变更及产物。发布副本从公开源撤出也有私密备份，不直接删除藏品记录。
6. 构建失败、取消及提交中途错误恢复已知前值；取消须等实际构建退出和恢复完成。遇到外部新内容、快照摘要不符或门禁归属不明时停在needs_review，不盲目覆盖，不伪报取消或成功。失败候选和证据不自动删除。
7. 进程重启不自动再次合并。根据持久日志核实：未提交的可恢复原状；已证明提交的保留结果并解除本次门禁。写入协调器只允许服务端验证合并日志后核对这类收据，不能用客户端自报结论解除其他类型的待核对操作。

## 公开旧链接和统计

- 新增公开投影只保存旧编号、当前公开主号及页序映射；不公开mergeId、操作者、账号、快照、磁盘路径或原全文。每次构建按当前主件文件名重算位置；目标撤下后不导出有效映射，已移除影像不能继续跳到旧图。
- 六语言旧入口生成独立的noindex去向页，按旧图片页号找到对应新页。它们不计为独立档案，不进入搜索目录、随机索引或sitemap；JavaScript从当前records摘要再核对映射，避免缓存旧页序造成误跳，且响应同页hashchange。非法页号不跳到另一幅图。
- 无脚本时保留明确的当前档案链接与逐页链接，HEAD可读取去向页。本阶段的多图去向页使用静态200页面；**未声称新增生产Caddy的302或缓存配置**。既有生产一次性合并去向、部署锁和服务配置须在第三阶段接入时逐项核对。
- 访客足迹只在其浏览器中按当前公开别名解析并去重，不上传历史；收藏及点赞则在各自既有业务存储/服务处理，不塞入档案元数据。

## 界面与接口

- 普通本机页继续只显示方案维护；明确开启内部模式后，才出现执行条件检查、合成预览、13项本人检查、输入保留编号和两项发布范围确认。全部默认未确认，不自动勾选。
- 执行进度显示日志里的实际阶段，支持取消并等待结果。网络响应丢失可通过原操作编号找回；sessionStorage只暂存操作编号，不存全文。已执行方案标记只读，可看私密结果和阶段日志，不再次合并。
- 新增本机内部接口：`POST /api/merge-review`、`POST /api/merge`、`GET /api/merge-result/:operationId/:stepId`、`GET /api/merges/:mergeId`、`POST /api/merge-recover`。沿用同源标记、原操作协议及实际维护身份；取消复用 `/api/cancel-operation`。线上这些接口均404。
- 私密目录沿用 `merges/`：plans/versions保存方案，commit-operations保存幂等去向，plan-commits保存只读结果关联，UUID目录保存review、manifest、文件前后副本、候选和旧dist。历史继续放入既有history目录。均不进入Git和公开产物。

## 当前边界和下一阶段

第二阶段在本地内部验收范围完成。没有触碰实际档案主库、真实档案JSON、发布图片或生产服务，没有安装依赖，没有自动清理真实资料。

第三阶段才处理撤销合并的后续修改/引用冲突、恢复草稿、通用功能开放前的各schema完整验收，以及生产部署锁、当前版本目录、独立账号/点赞服务、存量一次性合并映射和上线核查的接入。本阶段的本机dist交换不能冒充生产发布。**不提前进入第三阶段，不上线一般合并功能。**
