## 三、建议优先处理的五组事项

### 1. 开发工具依赖安全更新：应安排处理，但不是已确认的线上入侵

实际安装及锁文件中的 Vite 为8.2.2。只读 `npm audit --json --ignore-scripts` 报1个高危依赖包、关联6条公告，不是6个已被利用的线上漏洞。Astro为7.2.10，Sharp为0.35.5。

其中Windows编辑器启动相关问题的官方8.2分支修复版本为 **Vite 8.2.4**，不是Astro 8.2.4。相关公告见[Windows条件下的命令执行风险](https://github.com/vitejs/launch-editor/security/advisories/GHSA-587h-7wmj-h5pm)、[开发服务文件首四字节泄露](https://github.com/vitejs/vite/security/advisories/GHSA-vfpm-58rq-9qcg)。不同公告有不同触发条件，不能把单一平台/配置条件套到全部公告。

公开站使用静态产物和独立Node服务，本轮没有发现这些开发接口在生产可达的证据。建议优先评估现有依赖的最小兼容安全更新；不直接执行 `npm audit fix --force`，不盲目跨大版本。更新后跑现有测试、图片上传与正式构建，再单独安排上线。处理前继续不要把开发预览端口开放到互联网。

### 2. 账户上传并发容量保护：补在读取大文件之前

已确认新建账户投稿及保存投稿都先读取、解析整个上传表单，再进入存储及配额锁。普通免注册投稿已有“最多同时接收2个”的占位保护，账户投稿没有同类保护。

现有保护并非空白：必须登录、上传开关、每IP每600秒120次、24MiB请求上限、每图5MiB/合计20MiB校验、30秒请求超时、最多60连接，账户服务还有768M内存上限。缺的是“在读入大文件前就限制同时处理数量”，累计频率限制不能替代它。

理论上60个接近24MiB的请求，仅原始请求体就可能达到1440MiB；这不是实测峰值，**没有证据表明当前已因此崩溃，本轮也没有压测**。主要风险是账号服务暂时不可用，不能直接说静态公开站会一并停止。

建议复用简单的全局并发占位，并酌情增加单账号上限；失败、断连和取消都可靠释放占位，拒绝时给出可重试提示。用隔离的合成请求验收，不用真实账号或生产压测验证。

源码依据：`local-admin/account-server.mjs:333`、`:373`、`:553`、`:555`；`local-admin/submissions.mjs:631`、`:645`、`:655`、`:689`；`deployment/laojiumopian-accounts.service:32`。
