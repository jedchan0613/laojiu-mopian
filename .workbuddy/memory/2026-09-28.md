## 邮件服务：域名解析位置的更正与路径确定

在指导用户配置邮件服务时发现并更正了一个关键事实：

- 用户此前自称"域名解析在腾讯云"，实测（`nslookup -type=NS laojiumopian.com`）NS 记录为 `kipp.ns.cloudflare.com` / `laura.ns.cloudflare.com`——**解析在 Cloudflare，不在腾讯云**。
- 真实情况是：域名在 Cloudflare 注册并管理解析，网站只是托管在腾讯云香港服务器上，两者无关。
- **结论**：仍走 Resend（因未做 ICP 备案，腾讯云/阿里云邮件推送走不通），但加记录这一步从"手动填"变成用 Resend 的 **Auto configure**（登录 Cloudflare 授权后自动加好），对技术小白更友好。

已同步更正 `docs/email-service-setup-guide.md` 的"你的情况"与操作清单两节。

## 邮件服务：完成首次真实发信（已确认）

用户已注册 Resend、验证域名 `laojiumopian.com`、创建了 Sending access 密钥并填入本机 `local-admin/accounts/mail.env`（该目录已 gitignore）。

**踩到的环境坑（重要，会再遇到）**：

- 本机**直连不了境外接口**：`api.resend.com` DNS 可解析但 TCP 超时（非沙箱问题，非沙箱环境同样失败）。
- 环境变量里的 `HTTP(S)_PROXY=127.0.0.1:56662` 是内部代理，**不允许**访问 resend（CONNECT 返回 502）。
- **Node 的 fetch 不会自动使用系统代理**，这是报错根因。
- 实测本机浏览器所走的代理在 `127.0.0.1:15236`，经它访问 `api.resend.com` 返回 200。
- 对策：`mail-test.mjs` 增加 `LJM_MAIL_PROXY` 配置，设置后改用 `curl` 子进程经代理发送（请求体走 stdin，不落在命令行上）。已记入 `docs/email-service-setup-guide.md` 第六节。

**结果**：测试信已发出，Resend 返回消息编号 `01a0e86e-29e5-71fc-b471-60952bb7262f`；**用户已确认在 351717612@qq.com 收到**。

**结论**：域名验证、密钥权限、发信通道三件事全部确认可用，邮件服务这一环打通。跨项目经验（本机访问境外 API 的限制与对策）已同步写入 `~/.workbuddy/MEMORY.md`。
